# 美しさと軽さを同時に取る（美術パイプライン）

「モバイルなのに、なぜあんなに綺麗で、しかも滑らかなのか」を実装する時に読む。技術選定そのものは `web-stack.md`、体験の設計は `core/calm-experience.md`。

**このページの主張はひとつです。軽さは、美しさを削った結果ではなく、美術の方針を選んだ結果として手に入ります。** 逆に言えば、方針を決めずに作ってから最適化する順序では、この状態には到達できません。

## 1. 原理 — カメラを固定した瞬間、光は焼ける

動的なライティングが要る理由は、**カメラかライトか物体のどれかが動くから**です。3つとも動かないなら、光は事前に計算して焼き付けられます。

| 動くもの | 必要になるもの |
| :--- | :--- |
| カメラ・ライト・物体すべて | リアルタイムライティング、影、GI近似。**モバイルで最も高い** |
| 物体だけが動く | 静的な部分はベイク、動く物だけライティング |
| **どれも動かない（固定カメラ）** | **全部ベイク可能。実行時の照明計算はほぼゼロ** |

**固定カメラの体験的な代償**は `core/projection-as-rule.md` §3 に書きましたが、**性能面では一方的な利益**です。そしてこの利益は、そのまま**より凝った見た目**に再投資できます。「軽いから地味にする」ではなく、**「軽いから、焼き込んだ豪華さを載せられる」**という順序になります。

さらに固定カメラは2つ効きます。

- **見えない面を作らなくていい。** 裏側・底面・内部は存在しなくてよい。ポリゴン数の議論の前に、そもそも作らない
- **ドローコールが予測できる。** 画面に映るものが最初から確定しているので、バッチングの設計が事前に立つ

## 2. モニュメントバレーが実際にやったこと

技術的な選択として確認できるのは次の4点です（ustwo のテックディレクターによる説明）。

| やったこと | 意味 |
| :--- | :--- |
| **標準のサーフェスシェーダを使わず、自前のディレクショナルライティングモデルを書いた** | 見た目を統一しつつ、モバイルで必要十分な計算量に抑えた |
| **静的なアンビエントオクルージョンを、標準のライトマップ生成でベイク** | 実行時のコストなしで「塊としての実在感」を得た |
| **ビネットと擬似的なボリューメトリック光は、オーバードローで** | ポストプロセスを避け、半透明の重ねで空気を作った |
| **テクスチャを使わない方向へ寄せた** | メモリ・帯域・そして**制作工数**が丸ごと消える |

そして重要な経緯として、**初期はテクスチャありの「きれいで基本的な」見た目だったが、それが「死んでいる」と感じられ**、AO を足したことで質感が立った、と説明されています。§4 はこの話です。

## 3. Web（Three.js）での組み方

**順序が大事です。** 下から順に積んでください。逆順だと、後から効かなくなります。

```javascript
// ── 1. 正射投影で固定する（core/projection-as-rule.md と同じカメラ） ──
const camera = new THREE.OrthographicCamera(-d * aspect, d * aspect, d, -d, 0.1, 1000);

// ── 2. マテリアルはテクスチャを持たない。色は面ごとに ─────────────────
// MeshLambertMaterial は安価で、フラットな絵に合う。
// flatShading を true にすると、面ごとに法線が立って「折り紙」的な塊感が出る
const mat = new THREE.MeshLambertMaterial({ color: 0xE8D9C0, flatShading: true });

// ── 3. AO を焼いて、第2UVで貼る ────────────────────────────────
// ライティングそのものより、AO のほうが立体感への寄与が大きい。
// aoMap は uv2 を見るので、必ず uv2 を用意すること（ここを忘れて「効かない」が最多）
geometry.setAttribute('uv2', new THREE.BufferAttribute(geometry.attributes.uv.array, 2));
mat.aoMap = bakedAoTexture;
mat.aoMapIntensity = 1.0;   // 0.8〜1.2 で調整。上げるほど陰が濃く、重く見える

// ── 4. 光は2灯だけ。動かさない ───────────────────────────────
scene.add(new THREE.AmbientLight(0xBFD4E8, 0.6));            // 空の色を回り込みに
const key = new THREE.DirectionalLight(0xFFF0D8, 0.8);       // 太陽。影は落とさない
key.position.set(5, 10, 7);
scene.add(key);
// renderer.shadowMap.enabled は false のまま。影は AO とベイクで表現する

// ── 5. 空気は板で作る ─────────────────────────────────────
// ビネット・光芒・霞は、ポストプロセスではなく半透明の板を重ねるほうが軽い。
// ただし重ねた枚数だけフィルレートを食うので、フルスクリーンの板は 2〜3 枚まで
```

**`renderer.shadowMap.enabled = false` を最初に決めてください。** リアルタイム影はこの構成で最も高く、しかも AO があれば必要ありません。「後で切ればいい」と思って入れると、影ありきの構図になって切れなくなります。

## 4. 「きれいだけど死んでいる」を避ける

**フラットに塗っただけの3Dは、必ず死んで見えます。** 原因は3つで、どれも安く直ります。

| 症状の原因 | 対処 | コスト |
| :--- | :--- | :--- |
| **面ごとの明度差がない** | 上面・側面・正面で明度を明確に変える（上を明るく、側面を1段暗く）。ライティングに任せず、**マテリアルの色そのものを分ける**のが確実 | ゼロ |
| **接地部に陰がない** | AO をベイクする。物と物が接する線に陰が入るだけで、置かれている感じが出る | 焼く手間だけ |
| **全部が同じ距離に見える** | 遠くのものを空の色へ寄せる（フォグ）。**フォグの色と空の色を一致させる**こと。ずれると板に見える | ほぼゼロ |

**「テクスチャを足す」は最後の手段です。** 上の3つを飛ばしてテクスチャに逃げると、重くなったうえに、まだ死んで見えます。

**逆説的ですが、AO は光の表現ではなく形の表現です。** 影がある場所ではなく、**面と面が近い場所**が暗くなる。だから固定カメラでもライトを動かしても壊れず、費用対効果がこれだけ突出しています。

## 5. 3層に分けて、役割を混ぜない

奥行きのある画面（3Dのランナー、横スクロール、Z軸方向に迫ってくる構成）は、**手前・プレイ空間・遠景の3層に分け、層ごとに役割を1つだけ持たせます。**

**これは奥行きの演出のためではなく、読みやすさの分業です。** 混ぜた結果が「綺麗なのに遊びにくい」で、この症状の原因はほぼ常に層の混線です。

| 層 | 役割 | 触れるか | 明度・彩度 | 視差 | 描画コスト |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **フォアグラウンド**（手前） | 額縁。奥行きを誇張する | **絶対に触れない** | 暗いシルエット、または半透明 | ミドルより**速く** | 小さく保つ |
| **ミドルグラウンド**（プレイ空間） | ゲームのルールが完結する場所 | **ここだけ触れる** | **最高明度・最大コントラスト** | 基準（等速） | ここに全部使う |
| **バックグラウンド**（遠景） | 世界観と、進行方向の提示 | 触れない | 低彩度・低コントラスト。フォグ色へ寄せる | ミドルより**遅く** | **動的ライト0・完全ベイク** |

### 層ごとの規律

**ミドルグラウンド** — 操作できるもの、当たるもの、跳べるものは全部ここに置きます。**すべての即時フィードバック（ヒットストップ、着地の沈み込み、粒子）もここで完結させてください。** 他の層に散らすと、何に反応したのかが読めなくなります。彩度の高い1色（§6）を割り当てるのもこの層です。そして**境界を物理的に明確に**すること。曖昧な端は偽アフォーダンスの温床です。

**フォアグラウンド** — 規律はひとつだけ。**プレイヤーと、当たり判定のある領域を、1フレームたりとも隠さないこと。** 手前を横切る柱や葉は雰囲気に効きますが、隠した瞬間に「完全自己責任」が壊れます。**これは P0 です**（`simple/juice-and-feel.md` §9 の「自機が見えない瞬間がある」と同じ項目）。隠さずに奥行きだけ稼ぐには、画面の上下端・左右端に寄せ、暗いシルエットにして、判定領域には決して重ねないこと。

**バックグラウンド** — ここが担うのは Pre（予告）です。この先が開けるのか、上がるのか、何かが起きるのかを、**触れないものの形で先に見せる**（`simple/one-button-runner.md` §5）。逆に、**背景に「触れそうなもの」を置いてはいけません。** プレイヤーが背景の足場を跳ぼうとしたなら、その絵は失敗しています。

### 検証

- **画面をグレースケールにする。** ミドルグラウンドだけが明度で浮き上がっていれば合格。色を抜いた瞬間に地形と背景が溶けるなら、色だけで層を分けていたということです
- **最高速度で1フレーム止める。** プレイヤーと着地点が両方見えているか。フォアグラウンドの検証はこれだけで足ります
- **初見の人に「どこを走れそうか」を聞く。** ミドルグラウンド以外を指したら、層分けが伝わっていません

**縮退の順序は、フォアグラウンドが最初です**（§7）。額縁は削っても遊べますが、ミドルグラウンドは削れません。

## 6. 色をどう絞るか

- **1画面 4〜6色まで**（明度違いは1色と数える）。増やすほど「絵」から遠ざかります
- **章ごとに配色を変える**。使い捨ての構成（`core/calm-experience.md` §4）と噛み合い、章が変わったことを説明せずに伝えられます
- **彩度の高い色は1つだけ**。それを**プレイヤーが操作できるもの**に割り当てる。何を触れるかを、色だけで伝えられます
- **色のみで情報を伝えない**（男性の約8%が赤緑の識別に困難）。形・明度・動きを併用してください

## 7. 予算と縮退

固定カメラの前提で、モバイルWebでの出発点です。

| 項目 | 目安 |
| :--- | :--- |
| 1画面の三角形数 | **3万〜8万**（見えない面を作らないので、思ったより少なくて済む） |
| ドローコール | **50〜150**。マテリアルを共有してバッチングを効かせる |
| テクスチャ | **AO とライトマップだけ**。1024〜2048、KTX2 で圧縮 |
| フルスクリーンの半透明板 | **2〜3枚まで**（フィルレート） |
| リアルタイム影 | **0**（使わない） |
| 初期ロード | **2MB 以下**（`web-stack.md` §9） |
| 目標フレームレート | 安定 **60fps**。このジャンルは動きが遅いので 30fps でも成立するが、操作の追従感は落ちる |

**縮退のダイヤルは、この順で用意してください。**

1. 半透明の板を減らす（見た目の劣化が最も小さい）
2. AO テクスチャの解像度を半分に
3. レンダリング解像度を 0.75 倍に
4. パーティクルを止める

**ポリゴン数は最後です。** 形が変わると構図が変わり、このジャンルでは体験そのものが変わってしまいます。

## 8. さらに先へ進める

2014年に無かった、あるいは高すぎた選択肢のうち、**この構成と相性が良いもの**だけを挙げます。

| 手段 | 何が良くなるか | 注意 |
| :--- | :--- | :--- |
| **KTX2 / Basis 圧縮テクスチャ** | AO・ライトマップの転送量とVRAMが大きく減る | デコーダの読み込みが要る。小さいテクスチャ1枚だけなら逆効果 |
| **ライトプローブをベイクして動く物に適用** | 動くキャラだけが浮いて見える問題が消える | 固定カメラなら、プローブは数個で足りる |
| **SDF による柔らかい接地影** | リアルタイム影なしで、キャラの足元だけ影を落とせる | 板1枚。最も安く「乗っている感」が出る |
| **頂点カラー** | テクスチャを持たずに面ごとの色差を焼ける | 制作ツール側の対応が要る |
| **WebGPU** | 将来的な余地 | このジャンルでは**必要ありません**。対応状況の変動リスクだけ増える（`web-stack.md` §10） |

**逆に、入れないほうがよいもの**: リアルタイムGI、SSAO、被写界深度、モーションブラー。**どれも固定カメラでは焼けるか、そもそも要らないものです。** 実行時に計算する理由がありません。

## 9. 検証

| 検証 | 合格の目安 |
| :--- | :--- |
| **3分以上の連続稼働** | 発熱でフレームが落ちない（短時間の計測は実力より良く出る） |
| **ミドルレンジの実機** | 開発機ではなく、3〜4年前の端末で 30fps を割らない |
| **スクリーンショット1枚での評価** | 静止画で美しいか。このジャンルは動いていない時間のほうが長い |
| **色覚シミュレーション** | 赤緑の識別が難しい条件で、触れるものが判別できる |
| **AO を切って比較** | 切ると明確に「死ぬ」なら、AO が正しく効いている。変わらないなら焼けていない |

**最後の検証を必ずやってください。** `aoMap` は `uv2` が無いと**エラーも警告も出さずに効きません**。効いていないまま「なんか物足りない」と感じ、テクスチャやライトを足して重くする——という経路が、このジャンルで最もよくある失敗です。
