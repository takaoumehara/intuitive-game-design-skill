# 入力を抽象化する — タップ・口・手・足・全身を同じ1本の信号にする

**このスキルで扱うゲームの入力は、ほぼ全て「1つの連続量」と「その立ち上がり」に還元できます。**

指のタップも、口の開閉も、手の握りも、膝を上げる動作も、その場ジャンプも、ゲーム側から見れば同じものです。違うのは信号の**質**（遅れ、揺れ、疲れ、人前でやれるか）だけで、**意味**ではありません。

このページの目的はひとつ。**入力方式を後から差し替えても、ゲームを作り直さなくて済む形にすること。** 口で遊ぶゲームを作った後に「スマホのタップでも遊べるように」と言われた時、ここができていれば数値を変えるだけで済み、できていなければ全部書き直しになります。

1. 信号の契約 — ゲームが受け取ってよいもの

## 1. 信号の契約 — ゲームが受け取ってよいもの

ゲームのロジックは、**入力がどこから来たかを知ってはいけません。**

```text
// どの入力方式でもこの形を返す。ゲームはこれ以外を見ない
{
  value:      0.0〜1.0,   // 連続量（タップなら押している間 1.0）
  active:     true/false, // しきい値を越えているか（ヒステリシス適用後）
  justOn:     true/false, // このフレームで立ち上がったか
  justOff:    true/false, // このフレームで立ち下がったか
  heldTime:   秒,          // active になってからの経過時間
  confidence: 0.0〜1.0,   // 推定の確からしさ。タップは常に1.0
}
```

`justOn` を必ず持たせてください。連続量からイベントを合成するのは入力層の仕事で、**ゲーム側でしきい値を比較し始めた時点で、この分離は壊れます。**

`confidence` は「今この入力は信用できるか」です。カメラで顔を見失った、手が画面外へ出た、暗すぎる——これらを 0 に落とします。**タップなら常に 1.0 なので、ゲーム側のコードは何も変わりません。** これがあるとないとで、欠測時の扱いをゲーム全体に散らかさずに済みます。

| ゲーム側が書いてよい | 書いてはいけない |
| :--- | :--- |
| `if (input.justOn) jump()` | `if (mouthRatio > 0.35) jump()` |
| `if (input.active) glide()` | `if (jawOpen > 0.4) glide()` |
| `if (input.confidence < 0.5) pauseSoftly()` | `if (!faceDetected) pauseSoftly()` |

## 2. モダリティ比較表

**同じゲームでも、入力を変えると別の難易度になります。** 違いは以下の5列に集約されます。

| 入力 | 遅延 | 揺れ | 続けられる時間 | 人前 | 欠測 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **キー・ボタン** | 5〜20ms | なし | 数十分 | ◎ | しない |
| **画面タップ** | 10〜50ms | なし | 数十分 | ◎ | しない |
| **端末の傾き** | 20〜50ms | 小 | 数分（腕の保持） | △ | しない |
| **声（音量）** | 20〜60ms | 中（環境音に弱い） | 1〜2分 | **×** | 騒音で誤検出 |
| **カメラ：口の開閉** | 80〜150ms | 大 | **30〜60秒** | **×〜△** | する |
| **カメラ：手（握り・ピンチ）** | 80〜150ms | 大 | 1〜3分 | △ | する（枠外へ出る） |
| **カメラ：足上げ・膝上げ** | 100〜200ms | 大 | 30〜90秒 | × | する |
| **カメラ：その場ジャンプ** | 100〜200ms **＋ 身体慣性 300〜800ms** | 大 | **30〜60秒** | × | する |

**遅延の列と、続けられる時間の列が、設計を決めます。** 残りは失敗モードの話です。

全身動作では、推定の遅延に加えて**身体そのものの遅れ**が乗ります。「跳ぼう」と思ってから足が地面を離れるまでに数百msかかるので、合計の猶予は指の10倍近くになります。これは補正で消せる種類のものではありません。

**「人前」の列を軽視しないでください。** 口を大きく開ける、跳ぶ、声を出す——これらを必須にした時点で、プレイできる場所を設計で決めています。展示・自宅・配信が狙いなら問題なく、電車の中で遊んでほしいなら破綻です。

## 3. 移し替える時に変える5つの数値

入力を差し替える時に触るのは、**この5つだけ**であるべきです。これ以外に手が入るなら、抽象化が漏れています。

| 数値 | ボタン・タップ | カメラ（顔・手） | カメラ（全身） |
| :--- | :--- | :--- | :--- |
| **判定窓** | ±30〜45ms（Perfect） | **±150〜200ms** | **±200ms以上** |
| **予告（Pre）の長さ** | 400〜800ms | 800〜1200ms | **1.2〜2秒** |
| **ヒステリシスの差** | 0（不要） | 正規化値で **0.2** | 0.2〜0.3 |
| **休息の比率** | 0〜5% | **20〜25%** | **25〜35%** |
| **1プレイの長さ** | 制限なし | 60〜120秒 | 60〜90秒 |

**「難しくする」と「精度を要求する」を混同しないでください。** 全身入力で判定窓を狭めると、難易度が上がるのではなく**運ゲーになります**。全身で難易度を上げる正しい方法は、判定を狭めることではなく、**要求の間隔を詰めること**と**判断の数を増やすこと**です。

コヨーテタイム・入力バッファは、どの入力でも必要です（`../simple/juice-and-feel.md`、実装は `../../assets/juice-controller.js`）。ただし**バッファの長さは遅延に合わせて伸ばします**。タップで 100ms のバッファは、カメラ入力では 200〜250ms 相当の働きしかしません。

## 4. 難易度テーブルは入力ごとに別に持つ

**同じ地形が、タップでは簡単で、全身では通過不能になります。**

無限生成の制約（穴の幅、到達間隔、同時要求数）は、**そのモダリティの遅延と可動域から計算される値**です。1つのテーブルを共有すると、必ずどちらかが壊れます。

```javascript
// 入力ごとに1つ。生成側はこれを見る
const PROFILE = {
  tap:    { reactionMs: 250, windowMs: 45,  minGapMs: 350,  restRatio: 0.05 },
  face:   { reactionMs: 400, windowMs: 180, minGapMs: 700,  restRatio: 0.22 },
  body:   { reactionMs: 650, windowMs: 220, minGapMs: 1100, restRatio: 0.30 },
};
```

**`minGapMs`（次の要求までの最短間隔）が最も効きます。** これを守らないと、「反応できないのではなく、**前の動作が終わっていない**」という状態が起きます。プレイヤーからは「操作を受け付けていない」と見えますが、実際には身体がまだ戻っていません。

生成時の検証も入力ごとに回してください（`../simple/procedural-generation.md` §4）。**タップで検証済みのコースは、全身入力で検証済みではありません。**

## 5. タップで先に作る

**体を使う入力で最初から作らないでください。** 順序はこうです。

```
① タップ版で面白くする  →  ② 入力層だけ差し替える  →  ③ 5つの数値を調整する
```

理由は4つあります。

- **バグの切り分けができる。** 手触りが悪い時、それがメカニクスのせいか、しきい値のせいか、遅延のせいかを、同時には切り分けられません。タップ版が気持ちよければ、残りは入力層の問題だと確定します
- **タップ版が基準として残る。** 「カメラだとなぜか難しい」を、数値ではなく体験として比較できます
- **プレイテストの回数が出せる。** 顎や全身は数十秒で疲れるので、1人あたり数回しか試せません。タップなら何十回でも回せます
- **カメラを使えない人・許可しない人の経路になる。** これは後付けが最も難しい部分で、最初から二重に作っておくとほぼ無料で手に入ります

**逆順（体の入力で作ってから、後でタップを足す）は、ほぼ必ず作り直しになります。** 体の入力に合わせて緩く作った判定と長い予告が、タップでは間延びして退屈になるからです。難易度が「合わない」のではなく、**面白さの中心がずれます**。

## 6. 連続量にしかできないこと

抽象化した上で、**連続量を持つ入力にしかできない設計**もあります。使うなら意識的に使ってください。

| 使い方 | 例 |
| :--- | :--- |
| **量をそのまま量に写す** | 口の開き＝受け皿の大きさ、手の高さ＝自機の高さ、膝の高さ＝ジャンプ力 |
| **「途中」に意味を持たせる** | 半分開けた状態が第3の状態になる（開・半開・閉） |
| **姿勢を維持させる** | 「押しっぱなし」より身体的なコストが高く、緊張の演出に使える |

ただし**中間状態を判断に使うと、途端に難しくなります。** 推定の揺れがそのまま判断のブレになるからです。中間を使うなら、**視覚で今の値を返す**のが必須です（`camera-input.md` §6）。

そして**タップに移し替えられるかを常に確認してください。** 「口の開き具合で受け皿の大きさが変わる」は、タップでは「押している長さで大きさが変わる」に翻訳できます。翻訳できない設計は、そのモダリティに閉じた設計です。閉じること自体は選択として有効ですが、**選んだと自覚しているか**が分かれ目です。

## 7. 検証

**抽象化ができているかを判定する方法は1つです。**

> **入力層のファイルを1つ差し替えるだけで、同じゲームがタップで遊べるか。**

遊べないなら、ゲーム側にモダリティ固有の判断が漏れています。`jawOpen`、`landmark`、`ratio` といった名前がゲームロジックの中に出てきたら、そこが漏れている場所です。

| 検証 | 合格の目安 |
| :--- | :--- |
| **入力の差し替え** | 上記。1ファイルの交換で成立する |
| **プロファイルの差し替え** | 数値テーブルを変えるだけで、難易度が破綻しない |
| **欠測の注入** | `confidence` を強制的に 0 にしても、ゲームが壊れず、進行が止まる |
| **同一人物での比較** | 同じ人がタップ版と体験版を遊び、どちらも「同じゲーム」だと言う |

最後の1つが本命です。**別のゲームだと感じられたなら、それは入力を差し替えたのではなく、別のゲームを作っています。** それが狙いなら構いませんが、狙いでないなら、5つの数値のどれかが合っていません。
