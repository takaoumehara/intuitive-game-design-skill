# 複数人で同じ体験を共有する（同席・別端末）

「2人で遊べるようにしたい」「友達と一緒にやりたい」と言われた時に読む。

**先に結論を言います。同期の難しさの大半は、技術ではなく設計で消せます。** ネットワークの話に入る前に §1 を通してください。ここを飛ばして実装から入ると、消せたはずの難しさに数週間を使うことになります。

## 1. 「複数人対応」は3つの別問題

ユーザーの「一緒に遊びたい」は、たいていこの3つのどれかで、**実装コストは10倍ずつ違います。**

| 形 | 中身 | コスト | 何が得られるか |
| :--- | :--- | :--- | :--- |
| **非同期** | スコア共有、ゴースト（他人の過去の走行を再生）、同じシードのコースを別々に走る | **最小**（サーバーは記録の置き場だけ） | 「あいつに勝ちたい」。競争の感情のほとんどはここで出る |
| **同席** | 1台の画面／カメラの前に並ぶ | 小〜中（ネットワーク不要） | 隣で笑う。**同時入力の技**が作れる |
| **別端末リアルタイム** | それぞれの端末で同時に、互いが見える | **最大** | 離れた相手と、同じ瞬間を共有する |

**まず、一番安いもので目的が満たせないかを検討してください。** 「友達と競いたい」の相当部分は、ゴースト（前を走る半透明の影）と共有シードで満たせます。ネットワークの同期を一切書かずに、競争の感情だけを取れる構成です。

ゴーストは既に部品が揃っています。走行中の位置を一定間隔で記録し、次回それを再生するだけ（`../simple/one-button-runner.md` §9）。**相手が落ちても、切断しても、遅れても、何も壊れません。** リアルタイム同期が抱える問題を全部持たずに、「並んで走っている」だけを取り出せます。

## 2. 実装前に決める4つ

| 問い | 決めないと起きること |
| :--- | :--- |
| **同席か、別端末か** | 両方を同じ設計で満たそうとして、どちらでも中途半端になる。**同時入力の技は同席でしか成立せず**、離れた相手との共有は別端末でしか成立しません |
| **協力か、競争か**（両方は選ばない） | 「協力もできるし競争もできる」は、初見に何を目指せばいいか伝わりません（`../../workflows/mechanic-design-pipeline.md` の質問4） |
| **脱落をどう扱うか** | ここが最大の落とし穴。下記 |
| **何人か** | **2人と3人以上は使う技術が別物**です（§4.2）。「あとで人数を増やす」は設計変更であって、設定変更ではありません |

### 脱落者の時間は、設計項目です

**先に落ちた人が、残りを見ているだけになる構成を作らないでください。** 同席なら、その人は実際にその場に立ったまま手持ち無沙汰になります。別端末なら、黙って閉じます。

| 選択肢 | 向く場面 |
| :--- | :--- |
| **脱落を作らない**（落ちても復帰し、順位や距離で競う） | 既定の第一選択。1プレイが短いランナーなら、ほぼこれで足ります |
| **1プレイを短くする**（30〜60秒） | 待ち時間そのものを短くする。同席では最も効きます |
| **観戦に役割を与える**（残った人の妨害／援護、次のコースを選ぶ） | 脱落を残したい競技性がある時 |

**「最後まで残った人が勝ち」を選ぶなら、1プレイの長さは最初に落ちた人の待ち時間である**と考えてください。3分のステージで30秒目に脱落した人は、2分30秒何もしません。

## 3. 同席（1台の画面・1台のカメラに複数人）

ネットワークを書かずに複数人を実現できる、最も費用対効果の高い形。**同席にしかない価値は「全員同時の入力」です。** 全員が同時に口を開ける、全員が同時に手を上げる——これは離れた相手とは（遅延のせいで）成立しません。ここを設計の中心に置けば、同席を選んだ意味が出ます。

### 3.1 誰がプレイヤー1なのかを、途中で変えない

カメラに複数人を映して割り当てる時（MediaPipe なら `numFaces` / `numPoses` を人数分）、**最も多い事故がこれです。**

画面内の X 座標順で「左からP1, P2, P3」と毎フレーム割り当てると、**2人が横に交差した瞬間、全員の操作が入れ替わります。** 1人がフレームから外れて戻った時も同じことが起きます。プレイヤーからは「急に操作不能になった」としか見えず、原因の説明もつきません。

- **開始時に一度だけ割り当てて、以降は固定する。** 推定器が返すトラッキングIDがあればそれを使う
- **IDが無い／途切れる場合は、前フレームの位置に最も近い検出結果へ引き継ぐ**（位置による対応付け）。毎フレームのソート順で決め直さない
- **ロストしたプレイヤーの枠は空けたまま待つ。** 空いた番号に別人を繰り上げない
- **誰がどれかを画面で示す。** 各プレイヤーに色を割り当て、カメラのプレビュー上にその色の枠を出す。自分の入力が自分のものとして返っていることは、**この形では常に見えている必要があります**（`camera-input.md` §6 の複数人版）

### 3.2 人数を増やすと、認識そのものが痩せる

| 増えるもの | 実際に起きること |
| :--- | :--- |
| **推定コスト** | 検出人数にほぼ比例して増えます。1人で60fpsが出ていても、3人では推定が律速になり、**全員の遅延が増えます** |
| **1人あたりの画素数** | 3人を1画面に収めると、顔は1人時の 1/3 の幅しか映りません。細かい表情ほど落ちます |
| **必要な物理空間** | 横に3人並ぶには、カメラから 1.5〜2.5m と、それだけの横幅が要ります。**全身入力を3人分は、一般的な部屋では成立しません** |

**設計側の手当**は2つ。**推定を30fpsに固定して描画だけ60fpsで補間する**（`../web-stack.md`）。そして**人数が増えるほど、要求する動作を大きく・粗くする**（細かい表情の差ではなく、口を開けたか否かだけを見る）。判定のヒステリシス差も広げてください。

### 3.3 全員同時の入力（同席の主役）

全員が同時に同じ入力をした時にだけ起きること——大ジャンプ、画面全体の変化、障害物の消滅——を1つ作ってください。**同席の価値はここに集中します。**

| 設計項目 | 目安 |
| :--- | :--- |
| **同時とみなす窓** | **300〜500ms**。指のタップ（±50ms）の感覚で作ると、まず成立せず「反応しない技」になります |
| **成立の予告** | 誰か1人が入力した時点で、画面に「あと2人」に相当する視覚を出す。**予告なしでは、偶然以外で発動しません**（3層フィードバックの Pre） |
| **失敗の扱い** | 成立しなくても損をさせない。損があると誰も試さなくなります |
| **人数による補正** | 2人でも3人でも成立させる。人数が多いほど効果を大きくする（多いほど難しくなるため） |

## 4. 別端末（ネットワーク同期）

離れた相手と同時に遊ぶ場合。**ここから先は、設計で難しさを減らしてから技術を選びます。**

### 4.1 まず、送るデータを減らす設計にする

同期の難しさは、送るデータの量と、**ずれた時に何が壊れるか**で決まります。両方とも設計で下げられます。

**(1) コースをシードから決定論的に生成する。**
両者が同じシードから同じ地形を作れば、**地形は一切送らなくて済みます**（`../simple/procedural-generation.md`。生成器の `rng` は既に差し替え可能）。送るのは各自の位置と入力だけ。

- 決定論を壊すもの：`Math.random()` の直接呼び出し、フレームレート依存の物理（`dt` を掛け忘れた積分）、浮動小数の累積誤差、端末ごとに違う配列順
- **物理そのものを完全一致させる必要はありません。** 一致させるのは**地形**だけで、キャラクターの位置は送る——これが最も安い折衷です

**(2) 他人と物理的にぶつからない設計にする。**

**同期の問題の8割はここから来ます。** 他人と当たり判定を持つと、100msのずれが「当たっていないのに死んだ」になり、それを消すためにロールバックや遅延補償が必要になります。

**他人を半透明のゴーストにして、当たり判定を持たせないでください。** そうすると 100〜200ms のずれは誰も気づきません。並走しているように見え、追い抜きも分かり、それで競争は成立します。**この1つの決定が、実装量を桁で変えます。**

ぶつかることが体験の中心（押し合う、奪い合う）でない限り、これを選ばない理由はありません。

### 4.2 接続の3層

| 層 | 役割 | 注意 |
| :--- | :--- | :--- |
| **シグナリング** | 接続情報（SDP/ICE）を交換するだけ。合言葉やQRで部屋に入る | **短命で構いません**（数分で消える保管庫で足ります）。ゲーム中の通信はここを通りません |
| **P2P データチャネル**（WebRTC DataChannel） | 端末同士を直結。**同一国内で往復 20〜80ms**、サーバー費はほぼゼロ | **1対1でしか成立しません。** 3人以上をメッシュで繋ぐと接続数が N(N−1)/2 で増え、上り帯域が破綻します |
| **リレー**（WebSocket の星型中継） | 全員が中継サーバーに繋ぎ、送信者IDを付けて他全員へ転送 | **3人以上は実質これが必須。** 遅延は直結より上がる（往復が2脚になる）が、確実に繋がる |

**「2人で動いたから3人もすぐ」は成立しません。** 3人目を足すことは、通信方式そのものを変えることです。3人以上を将来やる可能性があるなら、**最初からリレー経由で作る**か、少なくとも送受信をリレーに差し替えられる形にしておいてください。

**直結が張れないネットワークが現実に存在します**（企業内、一部のモバイル回線）。直結だけの構成は「一部の人だけ繋がらない」を必ず生みます。直結を試し、駄目ならリレーへ落ちる二段構えが、体験としては最も安定します。

### 4.3 権威をどこに置くか

「誰が計算した結果を正とするか」。**これを決めないと、両者の画面が静かに食い違います。**

| 方式 | 中身 | 代償 |
| :--- | :--- | :--- |
| **ホスト権威** | 参加者の1台が世界を計算し、結果を配る。サーバー不要 | **ホストだけ遅延ゼロという不公平**。ホストが抜けると一瞬止まる。ホストの端末性能が全員に効く |
| **サーバー権威** | 中立のサーバーが計算する | 公平・改竄に強い。**常時動くサーバーの費用と運用**が要る |
| **各自権威**（当たり判定を共有しない） | 各自が自分の世界を計算し、位置だけ見せ合う | **§4.1(2) を選んだ場合はこれで足ります。** 最も安く、最も壊れない |

**ランナーやカジュアルな並走なら、まず各自権威を検討してください。** 競技として順位を保証する必要が出た時に初めて、ホスト権威やサーバー権威を考えます。

ホスト権威にするなら、**ホストが抜けた時に次の参加者へ引き継ぐ**処理を必ず作ってください（引き継ぎが無いと、ホストの回線が切れた瞬間に部屋が全滅します）。

### 4.4 送信レートと、遅延の隠し方

**60fps で送る必要はありません。** 送信頻度と描画頻度は別物で、間は補間で埋めます。

| 項目 | 目安 |
| :--- | :--- |
| 世界のスナップショット（ホスト → 全員） | **15〜20Hz**（50〜66ms間隔） |
| 自分の位置・入力（各自 → ホスト／全員） | **20〜30Hz** |
| 補間バッファ（他人を何ms過去として描くか） | **100ms 前後**。これがある限り、他人の動きはカクつきません |
| 1パケットに載せるもの | 位置・向き・状態フラグ・入力。**予測できるものは送らない** |

隠し方は3段階あり、**上から順に安いので、上で足りるなら下は要りません。**

1. **他人を過去として描く（補間）** — 受け取った位置を100ms遅らせて滑らかに繋ぐ。他人が少し過去にいることに、誰も気づきません
2. **自分だけ即座に動かす（クライアント予測）** — 自分の入力は往復を待たずに反映する。**自分の操作の手応えは、絶対に往復時間を待たせてはいけません**（100ms の Immediate 層はネットワークの都合を待ちません）
3. **巻き戻して再計算する（ロールバック）** — 格闘ゲームで使われる重い仕組み。**当たり判定を共有しないなら不要**です

### 4.5 参加の導線で、人は離脱します

同期が完璧でも、**繋ぐまでの手順で半分が消えます。**

- **合言葉は短く**（6桁程度）。長いIDを口頭やチャットで伝えさせない
- **QRとリンクを両方用意する。** 同じ部屋にいるならQR、離れているならリンク
- **相手を待っている間に何かできるようにする。** 待機画面で走れるだけで、体感待ち時間が変わります
- **失敗した時に何が起きたかを見せる。** 「接続できません」だけの画面はもう一度試されません。部屋が無い／満員／時間切れを区別してください
- **繋がるまでの上限を決める**（15〜20秒）。それを超えたら1人用へ落ちる導線を出す

### 4.6 運用で必ず要るもの

中継サーバーを出すなら、以下は「後で」ではなく最初に入れてください。**外に開いた口は必ず叩かれます。**

- **1接続あたりの送信レート・帯域の上限**（超えたら切断）
- **部屋の人数上限と、部屋の総数上限、部屋の寿命**（無操作で消える）
- **中継は中身を解釈しない設計にする。** 転送するだけなら、ゲームの仕様が変わってもサーバーを触らずに済みます
- **参加者のIPが相手に見えることを理解しておく。** P2P直結の性質上、相手に接続元が見えます。不特定多数とのランダムマッチでこれをやるなら、リレー経由を既定にしてください

## 5. どこまで作るかの判断

| 目的 | 作るもの |
| :--- | :--- |
| 友達に勝ちたい | **非同期**：共有シード＋スコア＋ゴースト（§1） |
| 同じ部屋で盛り上がりたい | **同席**：1画面／1カメラ＋全員同時の技（§3） |
| 離れた友達と並んで走りたい | **2人P2P＋各自権威＋ゴースト表現**（§4.1、§4.3） |
| 3〜4人で遊びたい | **リレー必須**（§4.2）。ここでサーバー運用が発生する |
| 順位を保証したい・競技にしたい | **サーバー権威**。ここまで来ると、ゲームの規模より運用の規模の話になります |

**1つ下の行で満たせないかを、必ず一度検討してください。** 上の行ほど、壊れる箇所が少なく、遅い回線でも成立します。

## 6. 検証

**開発機2つを同じ机の上で繋いだ結果は、何の保証にもなりません。**

| 検証 | 合格の目安 |
| :--- | :--- |
| **別のネットワークで繋ぐ** | 片方をモバイル回線にして成立する（直結が張れない場合の経路が動く） |
| **遅延を足す** | 往復 200〜300ms を人工的に足しても、遊べる（補間と予測が効いている） |
| **片方をバックグラウンドにする** | タブを裏に回すと `requestAnimationFrame` が止まります。戻した時に破綻せず追いつくか |
| **片方を落とす** | 回線を切る／閉じる。残った側が止まらず、引き継ぎか終了処理が働く |
| **同席：人が入れ替わる** | 2人が横に交差しても、操作の割り当てが入れ替わらない（§3.1） |
| **同席：1人が外れて戻る** | 番号が繰り上がらず、元の割り当てに戻る |
| **人数分の実測** | 最大人数で3分連続。**推定と描画の両方で発熱を見る**（`../web-stack.md`） |

## 7. 壊れる時の症状

| 症状 | 本当の原因 | 対処 |
| :--- | :--- | :--- |
| 「当たっていないのに死んだ」 | 他人と当たり判定を共有している | §4.1(2)。ゴースト表現にする |
| 他人の動きがカクつく | 補間していない（受信のたびに位置を代入している） | §4.4。100ms 遅らせて補間 |
| 自分の操作が重い | 入力を往復させてから反映している | §4.4。自分だけ即座に動かす |
| 途中から画面が食い違う | 決定論が壊れている（`Math.random()`／フレーム依存の物理） | §4.1(1)。シード付き乱数へ |
| ホストだけ強い | ホスト権威の構造的な不公平 | §4.3。各自権威かサーバー権威へ |
| 一部の人だけ繋がらない | 直結だけの構成 | §4.2。リレーへの二段構え |
| 3人目を足したら破綻した | メッシュ接続のまま人数を増やした | §4.2。星型リレーへ |
| 先に落ちた人が戻ってこない | 待ち時間が設計されていない | §2。脱落を作らないか、1プレイを短く |
| 同席で急に操作不能になる | 毎フレーム位置順で割り当て直している | §3.1。開始時に固定 |
| 同席で全員同時の技が出ない | 同時窓が狭い／予告が無い | §3.3。300〜500ms＋予告 |
| 繋ぐ前に人が消える | 参加の導線が長い・失敗理由が見えない | §4.5 |
