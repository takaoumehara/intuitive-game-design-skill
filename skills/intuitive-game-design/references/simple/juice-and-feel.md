# Juice — 手触りを詰める

メカニクスが動くようになった後、「なんか気持ちよくない」を解決する段階で読む。

**前提**: Juice はつまらないゲームを面白くしません。**面白いゲームを、面白いと感じられる状態にする**だけです。グレーボックスで面白くないなら、ここに来る前にメカニクスへ戻ってください。

## 1. 効く順番

全部やる必要はありません。**投資対効果はこの順**です。上から3つで、体感の8割が決まります。

| 順 | 要素 | 効果 | コスト |
| :-- | :--- | :--- | :--- |
| 1 | **ヒットストップ** | 打撃の重さ。最も安く最も効く | 極小 |
| 2 | **音の即応** | 押した瞬間に鳴る。無音は「壊れている」と解釈される | 小 |
| 3 | **スケール変形** | 生き物らしさ。跳ねる、潰れる | 小 |
| 4 | **画面シェイク** | 衝撃。ただし使いすぎると酔う | 小 |
| 5 | **パーティクル** | 華やかさ | 中 |
| 6 | **軌跡・残像** | 速度感 | 中 |
| 7 | **カメラワーク** | 状況の強調 | 大 |

**速度が変わり続けるゲーム（ランナー等）では、カメラだけは順位が違います。** そこではカメラは演出ではなく、プレイヤーが先を読むための時間そのものを決めるので、最初に決める項目になります（`one-button-runner.md` §4）。

## 2. ヒットストップ

**決定的な瞬間にゲーム全体の更新を止める。** 打撃の重さは、エフェクトの派手さではなく止まる時間で決まります。

| 用途 | 時間 |
| :--- | :--- |
| 軽い接触、コイン取得 | **2フレーム（約33ms）** |
| 通常の打撃、着地 | **3〜4フレーム（50〜67ms）** |
| 決定的な瞬間、ボス撃破 | **5フレーム（約83ms）** |
| これ以上 | 「固まった」「処理落ち」と感じられる |

実装は `assets/juice-controller.js` の `HitStop`。`dt` を 0 にして返すだけなので、ゲームループ側の変更は1行で済みます。

**止めるのは更新であって描画ではない。** 止まっている間もエフェクトやシェイクは動かすと、「止まった」ではなく「タメた」に感じられます。

## 3. 画面シェイク（Trauma モデル）

単純なランダム揺れは安っぽく感じます。**Trauma（打撃値 0〜1）を持ち、その二乗で振幅を決める**のが定石。

```
offset = maxOffset × trauma² × noise(time)
```

**なぜ二乗なのか**: 線形だと、弱い衝撃でも揺れが目立ち、強い衝撃との差がつきません。二乗にすると弱い衝撃はほとんど揺れず、強い衝撃だけが激しく揺れるので、**衝撃の強さが読めるようになります**。

**ランダムではなくノイズを使う**。毎フレーム `Math.random()` だと痙攣したような揺れになります。連続的なノイズ（`sin` の組み合わせでも十分）にすると滑らかに揺れます。

**回転も少し混ぜる**（0.05rad程度）。平行移動だけより格段に効きます。

### 使いすぎの基準
- 常時揺れている → 何も強調していないのと同じ
- 揺れで対象が見えなくなる → 完全自己責任の原則を壊す（**やめる**）
- **設定でオフにできるようにする**。3D酔いしやすい人がいます

## 4. スケールとスカッシュ

**動かすのではなく、変形させる。** 生き物らしさは、これがあるかないかでほぼ決まります。

| 場面 | 変形 | 戻り |
| :--- | :--- | :--- |
| ジャンプの踏切 | 縦に伸びる（1.0 → 1.3, 横 0.8） | 80ms |
| 着地の瞬間 | 潰れる（縦 0.7, 横 1.3） | 120ms |
| 取得・合成 | 一瞬膨らむ（1.0 → 1.2 → 1.0） | 150ms |
| 被弾 | 一瞬縮む＋点滅 | 100ms |

**戻る動きにイージングをかける**。リニアに戻すと機械的に見えます。`easeOutBack`（少し行き過ぎて戻る）が跳ねる感じに合います。

**体積を保つ**（縦に伸びたら横を縮める）と自然に見えます。これはアニメーションの古典的原則で、伸縮しても質量が変わらないという物理的な直感に合っているため。

## 5. パーティクルと軌跡

**数より配置。** 大量に出すより、正しい方向へ少数出すほうが効きます。

- **着地**: 足元から左右へ横方向に散る（下向きに出すと地面に埋まって見える）
- **加速**: 進行方向の逆へ
- **破壊**: 破片は**重力を受けて落ちる**。浮いて消えると軽く見える
- **取得**: 上へ（達成の方向は文化を問わず上）

**寿命は短く（200〜400ms）**。長いと画面が汚れ、次の情報が見えなくなります。

**軌跡（トレイル）は速度に比例させる**。常時出ていると速度感が伝わりません。

## 6. 音の連動

音の実装は `references/audio/`が扱います。ここでは**このジャンル特有の連動**だけ。

### 6.1 コンボでピッチを上げる

```
f_n = f_0 × 1.05^n
```

1音ごとに約1.05倍（半音の少し下）。**上がり続ける感覚**が、スコアの数字より強く「伸びている」を伝えます。

**上限を設ける**（12〜16音程度でリセット、またはオクターブで折り返す）。上げ続けると可聴域を超えるか、耳障りになります。

### 6.2 押したこと自体に必ず音を返す

判定の成否と切り離してください。**失敗時も「押した」音は返す。** 無反応は「自分が下手」ではなく「機械が壊れている」と解釈されます。

### 6.3 ヒットストップと音を揃える

止まる瞬間と音の立ち上がりが同時だと、衝撃が一つの出来事として知覚されます。ズレると2つの別々の出来事に感じられ、効果が半減します。

## 7. 触覚（ハプティクス）

**手に持っている端末で遊ぶゲームでは、触覚は音より確実に届きます。** 音を切っている人は多いが、端末は必ず手の中にあります。

### 強度の3段階

段階を分けないと、全部が同じ「ブッ」になり、情報にならなくなります。

| 場面 | 強さ | 長さ |
| :--- | :--- | :--- |
| ジャンプ・タップの受理 | **Light** | 10ms 程度。「押した」が返るだけでいい |
| 着地・取得・ブースト成功 | **Medium** | 20〜30ms |
| ミス・衝突 | **Heavy**（または2連） | 40〜60ms |

**入力の受理（Light）を省かないでください。** 判定の成否と切り離して、押したこと自体に返します。§6.2 と同じ理屈で、無反応は「自分が下手」ではなく「機械が壊れている」と解釈されます。

### Web では触覚を前提にできない

ここを知らずに設計すると、**iPhone だけ手応えが無いゲーム**が出荷されます。

| 環境 | 実情 |
| :--- | :--- |
| **iOS Safari** | `navigator.vibrate` が**存在しない**。呼んでも例外は出ず、何も起きない |
| **Android Chrome** | 動くが、ユーザー操作後のみ。強度指定は無く、長さだけ。10ms 未満は潰れる |
| **ネイティブ（iOS Core Haptics / Android VibrationEffect）** | 上の3段階を素直に表現できる |

したがって Web では、**触覚は「あれば良くなる」層であって、体験を支える層にはできません。** 重要な合図は必ず視覚か音でも返してください（これは同時にアクセシビリティの要件でもあります）。

```javascript
// 使えない環境で落ちない・鳴らないだけにする。呼び出し側で分岐させない
const HAPTIC = { light: 10, medium: 25, heavy: [40, 30, 40] };
function haptic(kind) {
  if (typeof navigator === 'undefined' || !navigator.vibrate) return; // iOS Safari はここで抜ける
  navigator.vibrate(HAPTIC[kind] ?? HAPTIC.light);
}
```

**連打しないこと。** 毎フレーム呼ぶと Android では振動が繋がって一本の連続振動になり、意味が消えるうえバッテリーを食います。**イベントの瞬間だけ**に限り、100ms 以内の再呼び出しは間引いてください。

**設定でオフにできるように。** 触覚を不快に感じる人、公共の場で遊ぶ人がいます。

## 8. リトライループ

**このジャンルで最も重要なのに、最も後回しにされる部分。**

死亡から次のプレイ開始まで **0.5秒以内・タップ1回**。ここが伸びると「もう一回」が起きません。

### やってはいけない構成

```
死亡 → 演出2秒 → リザルト画面 → 「リトライ」ボタンを探す → 読み込み → 開始
```

各ステップは小さくても、合計すると手が止まります。**手が止まった瞬間に、人はアプリを閉じます。**

### 推奨する構成

```
死亡 → 演出0.3秒（同時にスコア表示）→ 画面のどこでもタップ → 即開始
```

- **リザルトは死亡演出に重ねる。** 別画面にしない
- **タップ領域は画面全体。** ボタンを探させない
- **前回スコアと自己ベストを同じ画面に。** ニアミス（§2.2）の起動装置
- **読み込みを挟まない。** アセットは最初に確保しておく
- **到達地点を世界の中に残す。** 前回の死亡地点や自己ベストに目印（影・ライン・旗）を立てると、失敗がそのまま次回の目標になります。常時表示にはしないこと（`one-button-runner.md` §9）

**復帰後の状態をどこまで戻すかも、ここで決める設計項目です。** 速度・コンボ・所持アイテムを全部初期化すると、再到達までが毎回作業になります（`one-button-runner.md` §3）。

### 最初からやり直す代わりに、巻き戻す（Rewind）

**1プレイが長い構成（60秒超）やステージ制では、最初から始め直させると、到達までの数十秒が毎回作業になります。** その場合の代替が、数秒前の安全な地点へ時間を戻す復帰です。

| 向く | 向かない |
| :--- | :--- |
| 1プレイが長い／ステージ制／道中に見せ場がある | 1プレイ 20〜30秒のスコアアタック。**最初から始めるほうが速く、しかも公平**です |

**予算は、死亡から操作可能までの合計で 1.5秒以内。** 分解（停止 → 歪み → 巻き戻し）を凝るほど気持ちよくなりますが、**プレイヤーが数えているのは合計だけ**です。演出を3段構えにするなら、各段は 0.3〜0.5秒に抑えてください。

罠が3つあり、どれも「良かれと思って」踏みます。

1. **原因を見せずに巻き戻さない。** 即座に戻すと、なぜ死んだのかを見る時間がなくなり、**失敗が自分のせいだと感じられなくなります**（完全自己責任の崩壊）。死んだ瞬間で **0.3〜0.5秒止めて**、当たった場所を見せてから戻す
2. **無制限に巻き戻せるようにしない。** 失敗の代償がゼロになると、緊張ごと消えます。**消費する資源**にして（初期3個、中間地点で補充など）、残数を常に見せる
3. **戻す先を「◯秒前」で定義しない。** 死ぬ直前へ戻すと、同じ場所で死に続けるループになります。**「最後に安全な足場に接地していた時点」**で定義してください。時間ではなく状態で決めるのが要点です

実装は軽く済みます。**位置・速度・入力を 100ms 間隔でリングバッファに記録し、接地した瞬間に「安全な地点」の印を付ける**だけ。ゲーム状態を丸ごと保存する必要はありません。この記録は、そのままゴースト表示にも使えます（`one-button-runner.md` §9）。

**巻き戻しは逆再生で見せてください。** 一瞬で位置が変わると「何が起きたか」が伝わりません。0.4〜0.6秒かけて自分が戻っていくのが見えると、次にどこから始まるかも同時に理解できます。

### 広告を入れる場合
体験が固まってから、頻度を設計してから。**リトライの導線に広告を挟むと、このジャンルの中核が壊れます。** 挟むなら死亡数回に1回、かつスキップ可能に。

## 9. やりすぎの見分け方

Juice は足すほど良くなるわけではありません。以下が起きたら削ってください。

| 症状 | 何が起きているか |
| :--- | :--- |
| 自機や障害物が見えない瞬間がある | **完全自己責任の原則が壊れている。即座に削る** |
| 常に何かが光っている・揺れている | 強調が強調でなくなっている |
| 演出待ちで手が止まる | リトライループが伸びている |
| 上級者が演出を無視し始める | 判定領域に演出が被っている |
| プレイ動画が見づらい | 拡散の経路を自分で塞いでいる |

**判断の基準はひとつ。「その演出は、プレイヤーが次に何をすべきかを助けているか、邪魔しているか」。** 邪魔しているなら、どれだけ格好良くても削ります。
