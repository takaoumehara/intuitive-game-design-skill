# 直感性監査（Intuition Audit）

**経路B（既存のゲーム／プロトタイプの診断・改善）で使う手順書。** 「操作が分かりにくい」「チュートリアルが長い」「離脱される」「なぜ面白くないのか分からない」に答える。

プレイテスト（経路D）と違い、**被験者を集めずに机上で行う**。実データには劣るが、テストの前に潰せる問題を潰しておくと、貴重な被験者を本当に難しい問題へ使える。

---

## Step 0: 症状から仮説を立てる

ユーザーの訴えは、たいてい原因ではなく症状。**まず訴えの言葉から当たりをつける。** 経験上この対応はよく当たるので、監査の入口として使う。

| ユーザーの言葉 | 疑うべき第一容疑者 | 確認する場所 |
| :--- | :--- | :--- |
| 「理不尽」「見えなかった」「反応できない」 | **Pre フィードバックの欠落** | 敵の予備動作、ノーツの先読み距離、危険の予告 |
| 「反応しない」「重い」「押した気がしない」 | **Immediate フィードバックの欠落**、入力バッファ不足 | 入力から反応までの実測ms、成否と切り離した反応の有無 |
| 「手応えがない」「上手くなってる気がしない」 | **Post フィードバックの欠落**、成長の不可視 | 結果表示、スコア、成長の実感経路 |
| 「バグってる」「壊れてる」 | **偽アフォーダンス** | できそうでできないもの、装飾と機能の混同 |
| 「操作が覚えられない」「複雑」 | 同時新規要素が4超、反転マッピング | チュートリアル1回あたりの新規要素数 |
| 「チュートリアルが長い」 | **設計をテキストで埋めている** | チュートリアルの各行を消せない理由を1つずつ問う |
| 「作業感がある」「面倒」 | 情報過多／密結合の不足 | 選択に迷いがあるか、最適解が自明か |
| 「運ゲー」「理不尽」（結果に対して） | 情報飢餓／Pre 欠落 | 判断材料が結果の前に開示されているか |
| 「最初の画面で何をしていいか分からない」 | **初手30秒の設計不在** | 起動直後に動いているもの、可能な操作の数 |
| 「途中で飽きる」 | スキル3階層の停滞、フローの逸脱 | Manual / Situational / Mental のどこで止まっているか |

複数該当することが普通。**全部を並べず、下の採点で優先順位をつける。**

---

## Step 1: 情報を集める

監査対象の情報が不足している場合、以下を優先的に確認する。全部揃わなくても始められるが、**1と2がないまま診断すると当て推量になる**ので、この2つは必ず取りに行くこと。

1. **実際に触れるもの、または操作の映像**（最優先。仕様書からは体感が分からない）
2. **狙っている感情**（`mechanic-design-pipeline.md` Step 1 の質問1〜2。答えられないなら、それ自体が最大の発見）
3. 想定ターゲットと、その人の既存ゲーム経験
4. 現在のチュートリアル／説明の全文
5. 離脱データがあれば、どこで落ちているか
6. プラットフォーム（入力方式・想定プレイ環境・プレイ時間の長さ）

**触れないし映像もない場合**: そう明記した上で、仕様から読み取れる範囲で監査する。「実物を確認できていないため、Immediate フィードバックの項は評価不能」と正直に書く。**評価できないものを推測で採点しない。**

---

## Step 2: 10項目で採点する

各項目 **0 / 1 / 2 点**。合計20点。**根拠なしに点を付けない**（何を見てそう判断したかを1行で書く）。

| # | 項目 | 0点 | 1点 | 2点 |
| :-- | :--- | :--- | :--- | :--- |
| 1 | **初手30秒** | 何をすべきか分からない | 探せば分かる | 起動直後に自然と手が動く |
| 2 | **偽アフォーダンス** | できそうでできないものが複数 | 少数ある | 見た目と機能が完全に一致 |
| 3 | **同時新規要素** | 5つ以上を一度に要求 | 4つ前後 | 常に4以下、明確に分割 |
| 4 | **ナチュラルマッピング** | 覚えないと使えない操作が中心 | 一部が非直感的 | 説明なしで対応が推測できる |
| 5 | **Pre フィードバック** | 予告なしの事象がある | 一部で不足 | 全ての要求操作に予告がある |
| 6 | **Immediate フィードバック** | 入力に無反応な瞬間がある | 弱い／遅い | 100ms以内に必ず何か返る |
| 7 | **Post フィードバック** | 結果が分からない | 分かるが薄い | 結果と成長が明確に見える |
| 8 | **密結合／選択の深さ** | 最適解が自明、または選択がない | 一部にジレンマ | 常に「どちらも正しそう」がある |
| 9 | **説明への依存** | チュートリアルなしでは成立しない | 一部で必要 | 説明ゼロで中核が伝わる |
| 10 | **失敗の可読性** | なぜ失敗したか分からない | 推測できる | 原因が明示され、次の手が分かる |

### 点数の読み方

### 評価できない項目があった場合

実物に触れず仕様書だけで監査する時、Immediate フィードバックのように**原理的に採点できない項目**が出る。推測で点を埋めてはいけないが、点数を出さずに終わるとこの採点表は何の役にも立たない。両方を満たす書き方は次のとおり。

- 評価できた項目だけで採点し、**分母を実際に評価した項目数で書く**
- **20点満点に換算した参考値を必ず併記する**。これがないと §「点数の読み方」の判定表が使えず、採点した意味がなくなる
- 評価できなかった項目を列挙し、**それを評価するために何が必要か**を1行ずつ書く（「実機を1回触る」「初見の人1人に渡す」）

必ずこの1行を含めてください。**点数を出さずに終わらせないこと**が要点です。

```
評価できた6項目で 9/12点（20点満点換算：15点）。残り4項目は実機が必要。
```

換算式は `評価点 ÷ (評価項目数 × 2) × 20`。仕様書だけの監査では半分以上が評価不能になるのが普通なので、これは例外処理ではなく**通常運転**だと考えてください。

分母が10項目20点を大きく下回る（評価できた項目が6以下）なら、採点結果より先に「まず何を見せてほしいか」を伝えるほうが有益。

| 合計 | 状態 | 次にやること |
| :--- | :--- | :--- |
| **16〜20** | 直感性は達成されている | 面白さ・深さ（項目8）へ投資。実プレイテストで細部を詰める |
| **11〜15** | 部分的に破綻 | P0項目の個別修正。全体構造は維持してよい |
| **6〜10** | 説明で支えている状態 | チュートリアル削除を目標に、項目1・4・9を再設計 |
| **0〜5** | コアの見直しが必要 | 個別修正では回復しない。`mechanic-design-pipeline.md` Step 2 へ戻す |

**この点数は他のゲームとの比較用ではない。** 同じゲームの修正前後を比べ、投資対効果を判断するための道具として使う。

---

## Step 3: 真因を1つに絞る

低得点項目を全部並べても、ユーザーは動けない。**症状は複数でも、真因は1つか2つであることが多い。** 低得点項目を眺めて、以下のような連鎖がないか探す。

- 項目1・9 が低い → チュートリアルで初手を埋めている → **真因は項目4（マッピング）**。マッピングを直せば1・9が同時に上がる
- 項目5・10 が低い → 予告がないから原因も分からない → **真因は項目5**。10 は自動的に治る
- 項目3・8 が低い → 要素を足して深さを作ろうとしている → **真因は項目8の不在**。要素削減と密結合で両方が上がる
- 項目2・6 が低い → 「壊れている」という印象の二大要因が揃っている → 他より優先。**信頼が失われると他の改善が評価されない**

真因を特定できたら、**それだけを直した場合に何点になるかを見積もる**。この見積もりが、修正の説得力になる。

---

## Step 4: 修正案を出す

各修正案に、以下を必ず付ける。

| 必須項目 | 理由 |
| :--- | :--- |
| **対処レベル**（Real変更 / シグニファイア / 説明） | どのレベルで解いているかを明示すると、安易な説明追加が可視化される |
| **推定コスト**（小/中/大） | 「正しいが実装不能」な案は提案していないのと同じ |
| **効果の検証方法** | 観測可能な行動で書く。「分かりやすくなる」は検証方法ではない |
| **優先度**（P0〜P2） | 判断基準は下記 |

### 優先度の判断基準

- **P0**: 信頼が壊れる／離脱に直結する。偽アフォーダンス、無反応な入力、予告なしの即死、初手の不在
- **P1**: 体験を損なうが遊べる。フィードバックの弱さ、認知過負荷、失敗原因の不可読
- **P2**: 洗練の余地。演出の配置、選択の深さ、やり込みの導線

**「何人が遭遇するか」ではなく「遭遇した結果どうなるか」で決める**（`playtest-card-orid.md` 3章と同じ原則）。

## 出力テンプレート

```markdown
# [対象名] 直感性監査レポート

## 0. 監査の前提
- 確認したもの: [実プレイ / 映像 / 仕様書のみ]
- 評価できなかった項目とその理由: [...]

## 1. 結論（3行）
- 現状: [n]/20点。[一言で言うと何が起きているか]
- 真因: [1つか2つ]
- 最優先の一手: [これだけやるなら何をするか]

## 2. 採点
| # | 項目 | 点 | そう判断した根拠 |

## 3. 真因の連鎖
[どの項目がどの項目を引き起こしているか。真因を直した場合の推定点数]

## 4. 修正案
| 優先度 | 症状 | 修正案 | 対処レベル | コスト | 検証方法 |

## 5. 触らないほうがいいもの
[既に機能している要素。修正で壊さないよう明示する]
```

**セクション5を省略しない。** 監査レポートは指摘だけを並べると全否定に読まれ、実際にはうまくいっている部分まで作り直されることがある。**何が既に効いているかを名指すことは、指摘と同じくらい設計に貢献する。**
