# 見え方をルールにする — 不可能幾何とスクリーン空間の接続

「モニュメントバレーのような」と言われた時に読む。**あの構造の正体は美術ではなく、投影の扱い方です。**

普通のゲームは、3D空間の真実（どこに何があるか）を、カメラで見せます。この構成は逆で、**カメラに見えている配置のほうを真実として採用します。** 3D空間で繋がっていなくても、画面上で繋がって見えるなら、そこは繋がっている。

## 1. 何が起きているか

モニュメントバレー（ustwo, 2014）の実装から確認できることは、次の4点です。

- ゲームは**普通の3D**で作られ、カメラは**固定の正射投影**。構造物は**その1つの視点からしか意味を成さない**
- したがって**3Dワールド空間ではナビゲーションが成立しない**。歩ける面同士は物理的に繋がっておらず、**カメラから見て隣接しているだけ**
- 接続を手で書く案は破棄された（configuration が多すぎて非現実的）。代わりに**ナビゲーションのマークアップ・経路計画・移動処理を自作**し、マークアップはジオメトリに直接付いている
- キャラクターはパスの途中で**スクリーン空間上の次の点へテレポートする**。この結果、**フレーム精度のアニメーションサンプリング**が必要になった（Unity では legacy animation system へ戻している）

**最後の1点が、この構成の性格を全部語っています。** プレイヤーには連続した歩行に見えているものが、内部では毎回の瞬間移動です。**見えているほうが正しく、世界のほうが嘘をついている。**

### 錯覚が死ぬ条件はひとつ

**オクルージョン（手前の物に隠れる関係）の矛盾。** 接続と遮蔽の見えが1フレームでも食い違うと、プレイヤーはそこが繋がっていないことを理解してしまい、以後そのゲームの全ての床を疑い始めます。

これは「バグが目立つ」という話ではありません。**偽アフォーダンスの最も強い形**であり、一度起きたら取り返しがつかない種類の失敗です。

## 2. 実装の骨

Web（Three.js 想定）で最小構成を書くとこうなります。**要点は3つだけ**——正射投影を固定する、接続は投影座標で判定する、移動はスクリーン空間で連続にする。

```javascript
// ── 1. カメラを固定する。ここが動くと全部の接続が変わる ──────────────
// 正射投影であることが必須。透視投影だと、同じ「重なり」が画面内の位置で変わる
const d = 10;                                    // 表示範囲の半分
const camera = new THREE.OrthographicCamera(-d * aspect, d * aspect, d, -d, 0.1, 1000);
camera.position.set(20, 20, 20);                 // 等角に近い角度
camera.lookAt(0, 0, 0);

// ── 2. 歩ける点（ノード）を、投影した座標で結ぶ ──────────────────────
// 深度（カメラからの距離）は意図的に捨てる。それがこの構成の全て
const EPS = 0.06;   // 「同じ位置に見える」と見なす許容量（画面比）

function project(world) {
  const p = world.clone().project(camera);       // -1..1 の正規化デバイス座標
  return { x: p.x, y: p.y };                     // z は捨てる
}

function buildLinks(nodes) {
  const links = new Map(nodes.map(n => [n.id, []]));
  for (let i = 0; i < nodes.length; i++) {
    for (let j = i + 1; j < nodes.length; j++) {
      const a = project(nodes[i].world), b = project(nodes[j].world);
      if (Math.hypot(a.x - b.x, a.y - b.y) < EPS) {
        // 画面上で重なっている＝繋がっている。3D上の距離は一切見ない
        links.get(nodes[i].id).push(nodes[j].id);
        links.get(nodes[j].id).push(nodes[i].id);
      }
    }
  }
  return links;                                   // 経路探索は普通の BFS でよい
}

// ── 3. 移動は「画面上で連続」を保つ。ワールド座標は飛んでよい ──────────
function stepTo(actor, nextNode, t) {             // t: 0→1
  const from = project(actor.world), to = project(nextNode.world);
  const sx = from.x + (to.x - from.x) * t;        // 補間するのは投影座標のほう
  const sy = from.y + (to.y - from.y) * t;
  actor.setScreenPosition(sx, sy);                // 見た目はここで決まる
  // ワールド座標は、接地判定・遮蔽・影のために別途「今いる面」へ張り付ける。
  // t が 0.5 を超えた瞬間に所属を next 側へ切り替えると、遮蔽が正しくなる
  actor.world.copy(t < 0.5 ? actor.node.world : nextNode.world);
}
```

**`EPS` がこのジャンル唯一の魔法の数値です。**

| `EPS` | 起きること |
| :--- | :--- |
| 小さすぎる | 見た目には繋がっているのに歩けない。**プレイヤーは自分の目を疑う。最悪の状態** |
| **画面比 0.04〜0.08** | 出発点。キャラの足元サイズと同程度 |
| 大きすぎる | 繋がっていないところが繋がる。パズルの解が意図せず増える |

**大きすぎる側の事故は、テストで見つかりません。** プレイヤーが「なぜか解けてしまった」時、それは報告されないからです。§5 の自動検証で潰してください。

### アニメーションが破綻する理由と対策

ワールド座標が飛ぶので、**「前フレームの位置から今の位置を求める」タイプの処理が全部壊れます**。速度ベクトル、モーションブラー、トレイル、物理、ルート補間、全部です。

- **速度は投影座標から求める**（ワールドの差分を使わない）
- **アニメーションは時間で駆動する**（移動距離で駆動しない）。テレポートの瞬間に脚の位相が飛ぶと、それだけで嘘に見えます
- **パーティクルとトレイルはスクリーン空間で出す**か、テレポート時にリセットする

## 3. 固定カメラが得るもの・失うもの

**プレイヤーがカメラを回せないのは、制約ではありません。回した瞬間にゲームが消滅するからです。** これは弱点ではなく、この構成の定義です。

| 得るもの | 失うもの |
| :--- | :--- |
| 不可能幾何そのもの | 空間の把握（プレイヤーは立体を理解できない。理解させる必要もない） |
| **光を全部焼ける**（動的ライト・リアルタイム影が不要 → `../art-pipeline.md`） | 「見回して探す」楽しみ |
| 構図を1枚ずつ手で決められる（全画面が絵になる） | 使い回し。1章ぶんの構図は、その章でしか使えない |
| 描画負荷が読める（見えない面は最初から作らない） | 動的な演出（カメラワークで感情を作れない） |

**「失うもの」の3行目が、そのまま制作費になります。** 章ごとに構図を手で作るということは、章の数だけ美術の工数が線形に増えるということです。ここが後述の経済（`calm-experience.md` §6）に直結します。

## 4. 制作の反復速度を設計目標に置く

ustwo が明示していた目標は、**「レベルデザイナーがジオメトリを動かして再生すれば、追加作業なしでナビゲーションが通る」**ことでした。

**これは実装の都合ではなく、作品の質を決める判断です。** 不可能幾何は、頭で設計できません。**動かして、見て、「あ、繋がった」を拾う**のが唯一の作り方なので、1回の試行にかかる時間が、そのまま到達できる美しさの上限になります。

したがって、次を最初に作ってください。

- **接続はビルド時ではなく実行時に解く**（§2 の `buildLinks` を再生のたびに走らせる）
- **接続を画面に描くデバッグ表示**（ノードと辺を線で出す）。これが無いと、なぜ歩けないのかが永久に分かりません
- **カメラ角度を触れないようにロックする**。触れると必ず誰かが触り、全部壊れます

## 5. 検証 — 錯覚は自動で守れる

**この構成の失敗は、目視では見つかりません。** 以下は全部スクリプトで回せます。

| 検証 | 見つかるもの |
| :--- | :--- |
| **全ノード対の接続を列挙し、意図した辺と突き合わせる** | `EPS` が大きすぎて生まれた「意図しない近道」 |
| **ゴールへの到達可能性（BFS）** | 詰み。仕掛けの全状態の組み合わせで回すこと |
| **意図した解の手数と、実際の最短手数の比較** | 手数が短くなっていたら、そこに抜け道がある |
| **カメラを ±1°、±2° 動かして接続を再計算** | 「たまたま成立していた」接続。ここで消える辺は、実機の解像度やアスペクト比で壊れます |
| **アスペクト比を 4:3 / 16:9 / 20:9 で総当たり** | 端末によって解けない・解けてしまう事故 |
| **遮蔽の矛盾検出**: 接続のある2点間で、手前に別のメッシュが挟まっていないか | 錯覚が死ぬ唯一の条件（§1） |

**カメラを1°動かすテストが、このジャンル固有で最も効きます。** 成立が角度に対して脆い箇所は、設計として脆い箇所です。

## 6. さらに先へ進める4つの方向

2014年の条件で選ばれなかっただけの選択肢があります。**どれも「投影をルールにする」という核はそのままに、渡す自由を増やす方向です。**

### 6.1 視点を「連続で」回せるようにする

固定をやめ、プレイヤーがカメラを回せるようにすると、**接続が回転に応じて生まれては消えます**。パズルは「配置を変える」から「**見る角度を探す**」に変わります。

- 実装は §2 のままで、`buildLinks` を毎フレーム走らせるだけ（ノード数が数百なら十分間に合う）
- **危険がひとつだけあります。** 回転中に足元の接続が消えると、キャラが宙に浮くか落ちます。**回転中は移動を止める**か、**接続が消える角度で回転に抵抗をかける**（スナップの引力）
- 酔い対策として、回転は**連続ではなく段階（15°刻み等）＋イージング**にするほうが扱いやすい

**これを入れると、固定カメラで得ていた「光を全部焼ける」利点を失います**（`../art-pipeline.md` §2）。得るものと失うものを見比べてから決めてください。

### 6.2 投影の種類そのものを能力にする

正射と透視を切り替えられるようにすると、**「遠近が消えている間だけ繋がる橋」**が作れます。プレイヤーが持つのは移動能力ではなく、**世界の見え方を変える能力**になります。

透視投影では §2 の判定が使えない（同じ重なりが画面内の位置で変わる）ので、**投影行列を通した後の座標で判定する**実装に統一しておくと、切り替えが自然に通ります。

### 6.3 影を第2の投影として使う

光源方向への平行投影は、**もう1つの「見え方」**です。影の上を歩ける、影が繋がっている所だけ渡れる——実装は §2 の `project()` をライト空間に差し替えるだけで、**同じコードが2つのルールを生みます**。

太陽の角度を動かせるようにすると、6.1 の「角度を探す」を、カメラを固定したまま実現できます。**酔いのリスクが無いまま、探索の自由だけ増える**ので、費用対効果はこの4つで最も高いはずです。

### 6.4 視点の操作を身体に渡す

顔の傾き・姿勢で視点が動く構成にすると、**プレイヤーが身体を傾けて「繋がる角度」を探す**ことになります。実装は入力層を差し替えるだけです（`input-layer.md`）。

ただし遅延（80〜150ms）と揺れが乗るので、**接続の成立判定にヒステリシスが要ります**（`camera-input.md` §2）。揺れで接続が明滅すると、足場が点滅して見えます。

## 7. 壊れる時の症状

| 症状 | 原因 | 対処 |
| :--- | :--- | :--- |
| 繋がって見えるのに歩けない | `EPS` が小さい／ノードの打ち忘れ | §2。デバッグ表示を先に作る |
| 意図しない解が見つかる | `EPS` が大きい | §5 の最短手数比較 |
| 端末によって解ける／解けない | アスペクト比で投影が変わっている | §5 の総当たり |
| キャラの歩きが一瞬ガクつく | テレポート時にアニメの位相が飛んでいる | §2。時間駆動にする |
| トレイル・パーティクルが飛ぶ | ワールド座標の差分を使っている | §2。投影座標で出す |
| 「なんか嘘くさい」と言われる | 遮蔽の矛盾がどこかにある | §5 の遮蔽検出。1箇所でも致命 |
| 回転を入れたら落ちるようになった | 回転中に足元の接続が消えている | §6.1。回転中は移動を止める |
