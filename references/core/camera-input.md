# カメラを入力にする（顔・手・全身）

Webカメラで顔や身体を読み、それをコントローラにする時に読む。MediaPipe（Face Landmarker / Hand Landmarker / Pose Landmarker）を想定しているが、原理はどの推定器でも同じ。

**このページの前提**: カメラ入力は**センサではなく推定**です。ボタンは押されたか押されていないかのどちらかですが、推定は常に「たぶんこう」を返し、遅れ、揺れ、時々完全に外します。**その3つを設計で吸収しない限り、ユーザーには「反応が悪いゲーム」としてしか届きません。**

**ここはカメラ固有の実装だけを扱います。** 入力を差し替え可能にする設計（信号の形、モダリティごとの数値、タップ版との関係）は `input-layer.md` にあります。このページの仕事は、**カメラから 0〜1 のきれいな1本の信号を作ること**までで、そこから先はゲームがカメラを知らずに済むようにします。

## 1. 距離に依存しない値の作り方（口・手・膝・足）

生のランドマーク座標をそのまま使うと、**カメラに近づくだけで値が変わります。** 必ず「身体の中の比」に変換してください。

作り方はどの部位でも同じ3手順です。

1. **測りたい距離**を決める（口なら上下唇、手なら親指と人差し指、足なら膝と腰）
2. **基準になる身体の寸法**で割る（顔の大きさ、手のひらの幅、肩幅や身長）
3. キャリブレーション（§5）で個人差を吸収する

| 作りたい入力 | 測る距離 | 割る基準 |
| :--- | :--- | :--- |
| 口の開閉 | 上唇内側 ↔ 下唇内側 | 顔の縦寸法・目間距離 |
| 手の握り／ピンチ | 親指先 ↔ 人差し指先 | 手首 ↔ 中指付け根 |
| 手の高さ | 手首の Y | 肩 ↔ 腰の距離 |
| 膝上げ・もも上げ | 膝の Y − 腰の Y | 腰 ↔ 足首の距離 |
| その場ジャンプ | 腰の Y の変化量 | 立位時の腰の高さ |
| 上体の傾き | 肩の左右 Y 差 | 肩幅 |

**基準にする寸法は、その部位が動いても変わらないものを選んでください。** 膝の高さを「膝と足首の距離」で割ると、膝を上げた瞬間に分母まで変わって値が飽和します。

以下は口の例ですが、置き換えるのは距離の取り方だけです。

```javascript
// MediaPipe Face Landmarker のランドマーク番号
//   13 = 上唇の内側 / 14 = 下唇の内側 / 10 = 額の上端 / 152 = 顎先
//   33 = 右目尻 / 263 = 左目尻
const dist = (a, b) => Math.hypot(a.x - b.x, a.y - b.y, a.z - b.z);

// 正面を向いている時の基準寸法。キャリブレーション（§5）の最初の1.5秒で埋める
const ref = { faceH: 0, eyeW: 0 };

function faceScale(lm) {
  const faceH = dist(lm[10], lm[152]);   // 顔の縦寸法
  const eyeW  = dist(lm[33], lm[263]);   // 目間距離
  // 顔の縦寸法は「うなずく」と縮み、目間距離は「首を振る」と縮む。
  // 片方だけを分母にすると、その回転をしただけで口が開いたことになる。
  // 両方を基準と比べ、縮んでいないほう（＝回転の影響が小さいほう）を採用する。
  return Math.max(faceH / ref.faceH, eyeW / ref.eyeW);
}

function mouthRatio(lm) {
  return dist(lm[13], lm[14]) / (ref.faceH * faceScale(lm));
}
```

**「うなずくと口が開いたことになる」は、この種のゲームで最も多いバグです。** 顔の縦寸法だけで正規化すると必ず起きます。テストで見つけにくいのは、開発者が正面を向いたまま試すからです。

### ブレンドシェイプを使う選択肢

MediaPipe Face Landmarker は `outputFaceBlendshapes` を有効にすると `jawOpen` を含む係数を 0〜1 で返します。**すでに正規化され、頭の向きの影響も抑えられている**ので、自分で比を作るより安定します。

| | 自分で比を作る | ブレンドシェイプ |
| :--- | :--- | :--- |
| 計算コスト | ほぼゼロ | 追加の推論が乗る |
| 頭の回転への強さ | 対策を書く必要がある | 比較的強い |
| 挙動の見通し | 自分で全部見える | 中身は調整できない |
| 個人差 | 自分で正規化する（§5） | **それでも正規化は要る** |

どちらを選んでも §5 のキャリブレーションは必要です。**口の大きさ・開く量には大きな個人差があり、開発者本人の値を定数にすると、他人には反応しないゲームになります。** これは口に限りません。手の大きさ、脚の長さ、可動域、そもそも上げられる高さ——全て個人差のほうが大きい変数です。

### 微小な可動域を全画面に増幅する

位置で操作させる場合（顔の傾きで左右、手の位置で高さ）、**実際に動かす量は小さく保ってください。** 首を大きく振ると視線が画面から外れ、腕を大きく上げると数十秒で疲れます。

```javascript
// 可動域の上限を小さく取り、指数カーブで中央付近の感度を下げる
const MAX_TILT = 0.26;   // 約15度。ここまでで画面端に届く
const POWER    = 1.5;    // 1.0=線形。上げるほど中央付近が鈍く、端が速くなる
const n = Math.max(-1, Math.min(1, angleRad / MAX_TILT));
const x = Math.sign(n) * Math.pow(Math.abs(n), POWER) * halfWidth;
```

**`POWER` を 1.0（線形）にしないでください。** 中央付近が敏感すぎて、静止しているつもりでも自機が揺れ続けます。1.3〜1.8 あたりが扱いやすく、上げるほど「中央では落ち着き、端では速い」挙動になります。

## 2. しきい値はヒステリシスで持つ

単一のしきい値で「開いた／閉じた」を判定すると、**しきい値付近で状態が毎フレーム反転します**（チャタリング）。推定値は常に揺れているので、必ず起きます。

**開く時のしきい値と、閉じる時のしきい値を分けてください**（シュミットトリガ）。

```javascript
const OPEN_ENTER = 0.35;   // これを超えたら「開いた」
const OPEN_EXIT  = 0.15;   // これを下回るまで「開いた」まま
let isOpen = false;

function updateOpen(ratio) {
  if (!isOpen && ratio > OPEN_ENTER) isOpen = true;
  else if (isOpen && ratio < OPEN_EXIT) isOpen = false;
  return isOpen;   // 0.15〜0.35 の間では、直前の状態が維持される
}
```

| 数値 | 上げると | 下げると |
| :--- | :--- | :--- |
| 2つのしきい値の**差**（0.2 程度から） | 誤爆しないが、閉じるのが遅れて感じる | 反応は速いが、境界で震える |
| `OPEN_ENTER` | 大きく開かないと反応しない（顎が疲れる） | 喋っただけで発動する |

**差をゼロにしてはいけません。** 「たまに反応しない／勝手に反応する」の大半がこれです。

**最小保持時間（80〜120ms）を併用する**と、さらに安定します。ただし保持時間はそのまま入力遅延として乗るので、§4 の予算と合わせて決めてください。

## 3. 揺れを取ると遅れる — One Euro Filter

推定値の細かい揺れ（ジッター）は消したい。しかし移動平均やローパスで消すと、**速く動いた時に遅れます**。この2つは同じダイヤルの両端で、片方を良くすると片方が悪くなります。

**One Euro Filter は、その配分を「動きの速さ」で自動的に切り替えます。** ゆっくりの時は強くかけて震えを消し、速い時は弱めて追従させる。

| パラメータ | 役割 | 調整の方向 |
| :--- | :--- | :--- |
| `minCutoff`（**1.0 Hz** から） | 静止時のなめらかさ | 下げる → 静止時の震えが減る／動き出しが鈍る |
| `beta`（**0.007** から） | 速い動きへの追従 | 上げる → 遅れが減る／速い動きで震える |
| `dCutoff`（1.0 Hz） | 速度推定の平滑化 | ふつう触らない |

**調整の順番を守ってください。** ①`beta = 0` にして、静止させたまま `minCutoff` を下げ、震えが止まる値を見つける。②次に `beta` を上げ、速く動かした時の遅れが消えるところで止める。同時に動かすと、どちらが効いているか永遠に分かりません。

### カメラ 30fps と描画 60fps の差を埋める

推定は 30fps でしか更新されないのに、画面は 60fps で描かれます。値をそのまま入れると、**2フレームに1回だけ動く**カクついた動きになります。

```javascript
// 毎フレーム、目標値へ指数的に近づける（フレームレートに依存しない書き方）
const LAMBDA = 24.0;   // 大きいほど速く追いつく＝遅れは減るがカクつきが残る
current += (target - current) * (1 - Math.exp(-LAMBDA * dt));
```

**これは追加の遅れです。** 見た目のなめらかさのために遅延を足していることを自覚して、§4 の合計に含めてください。

## 4. 遅延の内訳と、要求してよい精度

**ここがこのページで最も重要です。** カメラ入力の遅延は、指の入力とは桁が違います。

| 段階 | 目安 |
| :--- | :--- |
| カメラのフレーム周期（30fps） | **33ms**（＋センサ側の遅延） |
| 推定の実行時間（GPU 利用時） | **10〜30ms**（モバイルはこれより大きいことがある） |
| フィルタの実効遅れ（One Euro） | **10〜40ms**（ゆっくり動くほど大きい） |
| 描画までの待ち | **16〜33ms** |
| **合計** | **おおむね 80〜150ms** |

この 80〜150ms は**消せません**。カメラを 60fps にしても、推定とフィルタは残ります。

### したがって、判定窓は「指の値」を使えません

`references/core/rhythm-and-synesthesia.md` §2.2 の層でいえば、カメラ入力は **Movement Buffer（±150〜200ms）** の側です。

**±33ms の Perfect 判定は、カメラ入力では成立しません。** 入力の揺れ幅より判定窓のほうが狭いので、判定結果はプレイヤーの技術ではなく運を測ることになります。しかもプレイヤーからは「タイミングは合っていたのに Miss になった」としか見えないため、完全自己責任の原則が壊れます。

**判定は必ず時間で定義してください。** 「距離が 0.3m 以内」のような距離ベースの判定は、速度が上がると時間窓が勝手に縮みます（速度 28m/s なら 0.3m は 11ms です）。距離で書かれた仕様を見たら、その場で時間に直してください。

### 遅延を隠す方法

消せない以上、隠すか、要求しないかのどちらかです。

- **予告を長くする**（Pre層を 800ms〜1.2秒前に）。判定の瞬間ではなく、**構える時間**を渡す
- **判定を「連続量」にする**。Perfect/Great/Miss の段階ではなく、「近いほど良い」の連続スコアにすると、遅延は順位ではなく点数の差として吸収されます
- **入力の意味を状態にする**（この瞬間に押した、ではなく、今どうしているか）。口の開閉、手の位置、姿勢は状態として読むほうが向いています

## 5. テキストなしの自動キャリブレーション

**個人差の吸収は必須ですが、設定画面でやらせてはいけません。** 「口を最大に開けてください」という指示は、初見の摩擦としては大きすぎます。

遊びの中で測ってください。

```text
[0.0〜1.5s] 何もしない状態を測る          → 最小値（安静時の値）を記録
[1.5〜3.0s] 反射的に動きたくなる状況を出す → その最大値を記録
[3.0s〜  ] 正規化して開始   value = (raw − min) / (max − min)
```

**最大値を引き出す「餌」は部位ごとに違います。** 口なら目の前に大きなものを近づける。手なら画面の高い位置で何かが光る。膝なら足元を何かが通過する。**共通しているのは、指示ではなく状況で動かしていること**です。

- **「やらせる」のではなく「やりたくなる」状況を作る**。これは説明ゼロで最大値が取れる唯一の方法です
- **測っている間もゲームは進んでいる**こと。計測画面を見せた時点でテキストなしの意味が消えます
- **max が min に近すぎたら測り直す**。ユーザーが何もしなかった場合、`max − min` がほぼ 0 になり、以降ゼロ除算か極端な過敏になります。安全な既定値へ落としてください
- **プレイ中も上限を更新し続ける**（記録した max を超えたら広げる）。疲れてくると動作は小さくなるので、下方向の追従は慎重に

## 6. 入力が届いていることを見せる

**ボタンと違い、カメラ入力には「押した感触」がありません。** 反応がない時、プレイヤーは「自分の動きが足りないのか」「認識されていないのか」「ゲームが壊れているのか」を区別できません。この不安は、遅延そのものより強く体験を壊します。

対策は2つで、**どちらも安く、効果が非常に大きい**部類です。

**1. 自分の映像を小さく出す（ミラー表示）**

画面の隅にカメラ映像を小さく鏡像で置き、**その上に推定結果（口の輪郭、手の骨格、姿勢の線）を重ねて描く。** 認識されているかが一目で分かり、位置や明るさを自分で直せるようになります。

- **左右反転（ミラー）は必須。** 反転していないと、自分の動きと画面が逆になり、位置合わせが不可能になります
- **小さく、隅に、半透明で。** 主役はゲームです
- **推定結果を必ず重ねる。** 映像だけだと「映っている」ことしか分からず、「認識されている」ことが分かりません

**2. 入力の現在値を、ゲーム世界の中に出す**

しきい値の手前でも、今どのくらいの値かが見えるようにします。判定面に置いたリングの大きさを入力値に連動させる、自機のスケールを連動させる、ゲージを出す——**手段は何でも構いませんが、「もう少しで届く」が見えること**が要点です。

これは §2 のヒステリシスと組みで効きます。**しきい値が2つあることをプレイヤーは知りませんが、「今どのくらいか」が見えていれば、身体が勝手に学習します。**

**タップ版には不要な要素です。** 入力方式ごとに増える UI なので、入力層と一緒に差し替えてください（`input-layer.md`）。

## 7. トラッキングが外れた時

**顔や手は必ずフレームから外れます。** 振り向く、暗い、逆光、眼鏡の反射、マスク、他の人が映り込む、子どもが手を振る。

設計しておくべきは3つ。

| 状況 | 設計 |
| :--- | :--- |
| **短い欠測（数フレーム）** | 直前の値を保持する。ゼロに落とすと、一瞬だけ入力が暴れて誤爆します |
| **長い欠測（0.5秒以上）** | ゲームを止める。「カメラに顔が見えません」を**テキストではなく画面の縁の表示**で返し、復帰したら自動で再開する |
| **複数人が映る** | どの顔を使うか決め、**それを画面に示す**（枠を出す）。黙って切り替わると、原因不明の暴走に見えます |

**割り当ては開始時に固定し、毎フレーム決め直さないこと。** 画面内の位置順（左から順）で毎フレーム割り当てると、2人が横に交差した瞬間に操作が入れ替わります。1人だけを使う設計でも、後ろを人が通っただけで乗り換わります。**意図的に複数人を同時に遊ばせる場合**の割り当て・人数による認識精度の低下・全員同時の入力は `multiplayer-sync.md` §3。

**欠測中にゲームを進めないこと。** プレイヤーは自分が操作できていないのに死んだと感じ、これは理不尽の中でも最も強い種類です。

**完全停止より、まず減速。** 急に止めるとテンポが切れ、復帰後に状況を再把握し直すことになります。欠測を検知したら、まず**進行を 0.3〜0.5倍に落とし**、それでも戻らなければ止める。多くの欠測は数フレームで復帰するので、減速だけで済み、プレイヤーは「一瞬もたついた」としか感じません。

**明るさは設計要件です。** 暗所でフレームレートが落ちる（露光時間が伸びる）ため、暗い部屋では遅延そのものが増えます。初回に一度だけ、明るさが足りない時に画面全体の色で伝えてください。

## 8. 身体の疲労と、人前でやれるか

### 顎・腕・脚は数十秒で疲れる

口を開ける、腕を上げる、膝を上げる、その場で跳ぶ——**指と違い、これらは重力に逆らう筋肉の仕事**です。連続で要求すると1分持ちません。

| 部位 | 連続して要求できる時間 | 休息の比率 |
| :--- | :--- | :--- |
| 指（タップ） | 数十分 | 0〜5% |
| 顎（口の開閉） | **30〜60秒** | 20〜25% |
| 腕・手（上げ続ける） | 1〜3分 | 20% |
| 脚・全身（膝上げ・跳躍） | **30〜90秒** | 25〜35% |

**1プレイの長さもここで決まります。** 全身を使うなら 60〜90秒、顔なら 60〜120秒を上限として設計してください。これを超える設計は、上手い人ほど身体が先に限界に達するという、上達を否定する構造になります。

- **休息を総プレイ時間の比率で確保する**（上表）。10〜15秒に一度、**何もしないことが正解**の区間を置く
- **休息を「無操作」として設計する**（避ける区間、滑空する区間）。ボタンでいう「押さない選択」と同じ扱いにすると、休息が退屈になりません
- **既定状態を安静姿勢にする。** 「口を閉じている」「腕を下ろしている」が通常で、動かした時だけ何かが起きる設計にしてください。逆にすると、常時筋肉を使い続けることになります
- **疲労で入力の質が落ちることを前提に**。後半ほど動作は小さくなるので、しきい値を固定していると「後半だけ反応しない」と言われます（§5 の追従）

### 人前でできない動作を必須にしない

**身体を使う操作の最大の制約は、精度ではなく恥ずかしさです。** 電車の中で口を大きく開ける人も、その場で跳ぶ人もいません。これは「そういう人もいる」ではなく、**プレイできる場所を設計で決めている**ということです。

- 大きく口を開ける、大声を出す、立ち上がる、跳ぶ——これらを必須にした時点で、プレイ場所は自宅か展示会場に限定されます
- **必要な物理空間も要件です。** 全身入力は、カメラから 1.5〜2.5m 離れて全身が映る場所を要求します。机の前では成立しません
- それが狙いなら問題ありません（展示・パーティ・配信）。**狙っていないなら、動作の大きさを下げるか、代替入力を用意してください**

### 代替入力を必ず用意する

顔・手・身体が使えない人がいます。カメラを許可しない人もいます。**タップでも遊べる経路を残してください。** カメラ入力を「体験の全部」ではなく「入力方式の1つ」として設計すると、これは自然に満たされます（`input-layer.md`）。

## 9. プライバシーと同意

**カメラ映像は、扱いを間違えると設計の善し悪しより先に信頼を壊します。**

- **推論をローカルで完結させるなら、そう明示する。** 「映像は端末の外に出ません」の1行があるかないかで、許可率が変わります
- **裏で撮って持っておかない。** スコア画面に使うつもりでも、本人が知らないうちにフレームを保存している状態は、共有しなくても裏切りです
- **保存・共有は必ず本人の明示的な操作の後。** 「共有する」を押した後にキャプチャする、あるいは撮った画像をプレビューして本人が選べるようにする
- **カメラが動作中であることを画面で示す。** ブラウザのインジケータ任せにしない
- **許可を求める前に理由を見せる。** いきなり `getUserMedia` を呼ぶと拒否されます。何のために使うかを1画面見せてから求めるほうが、許可率は明確に高くなります
- **拒否された後の経路を作る。** 拒否は失敗ではなく分岐です。そこで詰むなら、それは設計の欠落です

顔画像・顔の特徴量は、地域によっては生体情報として通常の個人情報より厳しく扱われます。**保存・送信・第三者提供を伴うなら、実装前に適用される規制の確認を促してください**（このスキルは法的助言をしません）。

## 10. 検証

カメラ入力は、開発者の環境で完璧に動き、他人の環境で動きません。**以下は全て、開発者以外で試してください。**

| 検証 | 合格の目安 |
| :--- | :--- |
| **正面以外を向く** | うなずく・首を振る動作で、入力が誤発動しない（§1） |
| **距離を変える** | カメラから 40cm と 120cm で、同じ動作が同じ値になる |
| **明るさを変える** | 逆光・暗所で、遅延の増加とロスト時の挙動が設計通り（§7） |
| **眼鏡・マスク・帽子・服装** | 検出が落ちる条件を把握しておく（直せなくても、把握していないのは別問題） |
| **身体の個人差** | 開発者以外の3人以上でキャリブレーションが成立する（§5）。全身なら身長差も |
| **3分間の連続プレイ** | 疲労で入力量が落ちても遊べる（§8）。同時に発熱も見る |
| **遅延の実測** | 動作から画面反映までを撮影して数える。**推測しない**（§4） |
| **タップ版との比較** | 入力層を差し替えて同じゲームが成立する（`input-layer.md` §7） |

**遅延の実測は、カメラでゲーム画面と自分の顔を同時に撮るのが最も確実です**（60fps 以上で撮影し、フレーム数を数える）。ここを測らずに判定窓を決めているプロジェクトが大半で、後半の「なぜか難しい」の原因はほぼここにあります。
