# 1ボタン・ランナーの解剖（2D / 3D）

「押したら跳ぶ、あとは自動で前進」に決まった時に読む。極小ゲームの中で最も要求が多く、最も**同じ失敗の仕方をする**構成。

**「1ボタン」は指のタップに限りません。** 口の開閉、手の握り、膝上げ、その場ジャンプ——このページの内容は全て、**1つの入力が立ち上がった瞬間**に対して書かれています。入力方式を変える時に触るのは §4 の猶予と判定の数値だけで、構造は変わりません（`../core/input-layer.md`）。以下では代表として「タップ」と書きます。

物理の実装は `mechanics-and-physics.md`、演出の詰めは `juice-and-feel.md`、地形生成は `procedural-generation.md` にある。ここはそれらを**ランナーという構成に組み上げる時にだけ問題になること**を扱う。

## 1. 中毒性の構造式

このジャンルが50年間同じ形で当たり続けている理由は、3つの掛け算に集約できる。

```
極小の入力（1タップ） × 即時かつ過剰な出力（音・光・加速） × 失敗からの即時復帰
```

**足し算ではなく掛け算**なので、どれか1つが0だと全体が0になる。よくある壊れ方はこう。

| どれが0になったか | プレイヤーが言うこと |
| :--- | :--- |
| 入力が極小でない（2つ目のボタンを足した） | 「操作が忙しい」「よく分からないうちに死ぬ」 |
| 出力が即時でない（演出が入力より遅れる） | 「反応しない」「重い」 |
| 復帰が即時でない（リザルト画面を挟んだ） | 何も言わずに閉じる |

3つ目が最も見つけにくい。**離脱は不満として言語化されない**ので、アンケートには出てこない。リトライまでの秒数を計測してください（`juice-and-feel.md` §8）。

### 認知的に何が起きているか

複数ボタンのゲームは「見る → **どれを押すか決める** → 押す」の3ステップで、真ん中に選択反応時間（約350〜400ms）が要る。1ボタンは「見る → 押す」の2ステップで、単純反応時間（約200ms）しか要らない。

**この中間の1ステップが消えることが、没入の正体**であって、シンプルさそのものが正体ではない。だから「1ボタンだが、押すタイミングによって3種類の意味がある」を**プレイヤーが判断しなければならない形**で作ると、ボタンは1つのままでも選択反応時間が戻ってきて、この構成の利点が消える。次の §2 はここが全て。

## 2. 1入力を「文脈」で多義化する

名作ランナーは全て、1つの入力に複数の意味を持たせている。ただし持たせ方に条件がある。

| 文脈 | 入力 | 起きること | 例 |
| :--- | :--- | :--- | :--- |
| 接地中 | タップ | ジャンプ（押した長さで高さが変わる） | ほぼ全て |
| 空中 | 長押し | 回転・アクロバット。着地を決めればブースト、回転中に着地すればミス | Alto |
| 壁に接触中 | タップ | 反転ジャンプ（壁蹴り） | Super Mario Run |
| 空中のリング／パッド上 | タップ | 追加跳躍 | Geometry Dash |
| 敵の頭上 | タップ | 踏みつけ＋大ジャンプ | Super Mario Run |

**これは「メカニクスを2つ入れる」ことではない。** ルールは1つのまま——「押すと跳ぶ」。増えているのは**プレイヤーが立っている場所**であって、覚えるべき操作ではない。

### 成立条件はひとつだけ

**分岐の根拠が、押す前に画面上で見えていること。**

「地面の上にいる」「壁の横にいる」「空中にいる」「リングの中にいる」は、全て見れば分かる。だから分岐は学習されるし、失敗も自分のせいになる。

逆に、**見えない内部状態で意味を変えてはいけない**。コンボ数、経過時間、直前の入力履歴、内部フラグ——これらで挙動が変わると、プレイヤーからは「**たまに変な動きをする**」としか報告されません。バグ報告として届くので、設計の問題だと気づくまでに時間がかかります。

### 追加するかどうかの判断

文脈を1つ足すたびに、**その文脈を初見で見分けられるかを別途検証**してください。リングは光っている、壁は縦に長い、敵は動いている——見分けの手がかりが無いなら、その文脈は足せません。

順序としては、**可変ジャンプ1つで面白くなってから**足す。可変ジャンプが面白くない状態で文脈を足すと、面白くない理由が分からなくなります。

## 3. 成功が速度で報われるループ

このジャンルの核心。**成功の報酬をスコアではなく速度で払う。**

| 作品 | 成功 | 報酬 |
| :--- | :--- | :--- |
| Canabalt | ノーミスで跳び続ける | 加速し続ける（接触・着地ミスで減速） |
| Alto | 空中回転を決めて着地する | マフラーが伸びてブースト |
| Geometry Dash | ジャンプが曲のリズムに乗る | 音楽が途切れず続く（＝演奏の継続そのものが報酬） |

**なぜ速度が報酬として強いのか**: スコアは画面の隅の数字だが、速度は**世界の見え方そのものが変わる**。報酬を受け取ったことを、数字を読まずに全身で知覚できる。しかも次の入力の手触りまで変わるので、報酬が体験の中に溶けている。

### 速度は報酬であると同時に難易度である

これが自動難易度調整として機能する。**上手い人ほど速くなり、速くなるほど難しくなる**ので、全員が自分の限界付近で遊ぶことになります（フロー状態）。難易度テーブルを書かずに難易度カーブが手に入る、極めて安い仕組み。

ただし副作用がある。**報酬が罰に転化する**。速くなった直後は最も死にやすい。ここを放置すると「頑張るほど酷い目に遭う」構造になります。

| 対策 | やること |
| :--- | :--- |
| **速度に漸近上限を置く** | 上限に近づくほど加速量を減らす（`procedural-generation.md` §3）。人間の限界を超えさせない |
| **回避の成功にも払う** | 下記のニアミス |
| **加速の直後に易しい地形を出す** | ブースト発動から1〜2チャンクは難易度を下げる。報酬を味わう時間を作る |
| **死亡時の速度の戻しすぎに注意** | 下記 |

### 「避けた」にも報酬を払う（ニアミス）

**跳んで越えた時だけ報酬を出すと、避ける・見送る・待つといった行動が無報酬になります。** その結果、プレイヤーは常に入力し続けるほうが得だと学習し、緩急が消えます。

危険物のすぐ脇を通過した、ぎりぎりで見送った、当たる寸前でかわした——**この瞬間に、小さくても確実な報酬（音・光・わずかな加速）を返してください。**

- **判定は「当たらなかった」ではなく「近かった」で取る。** 当たり判定より一回り大きい帯を通過し、かつ接触しなかった時に成立させます
- **見た目を判定より大きく描く。** かすった感覚は、実際の接触ではなく**見た目の近さ**から生まれます。判定を小さく、見た目を大きくすると、安全なのにスリルがある状態が作れます
- **報酬は小さく、頻度は高く。** 大きくすると、わざと危険に近づくのが最適解になり、避けるゲームではなくなります

これは「押さない選択」に報酬を与える実装です（`mechanics-and-physics.md` §6）。**入力を増やさずに、判断を1つ増やす**最も安い方法。

### 死亡時に速度をどこまで戻すか

**ここの設計を飛ばすと、リトライの手触りが決まらない。**

| 戻し方 | 起きること |
| :--- | :--- |
| 初速まで全部戻す | 到達までの数十秒が毎回作業になる。上手い人から順に辞める |
| まったく戻さない | 死んだ速度で再開するので即死ループになる |
| **直前速度の 60〜75%**（推奨の出発点） | 助走が短く、かつ立て直せる |

ハイスコアが遠い設計ほど戻し量を小さく、1回が短い設計ほど大きくする。**「死んだ地点までの再到達に何秒かかるか」を実測して決めてください。** 20秒を超えると明確に嫌がられます。

## 4. 速度は先読み時間を食う — 視点とFOVの本当の理由

速度を上げると、障害物が視界に入ってから対応が必要になるまでの猶予が縮む。**猶予が反応時間を下回った瞬間、そのゲームは理不尽になります。**

```
必要な可視距離 D = v × (t_反応 + t_入力猶予 + t_跳躍の移動分)
```

| 猶予 | 体験 |
| :--- | :--- |
| **400ms 未満** | 反応が間に合わない。「見えた時にはもう遅い」＝理不尽 |
| **600〜800ms** | 快適。見て、決めて、押せる |
| **1500ms 以上** | 退屈。緊張が続かない |

**この表はタップの値です。** 入力が身体になると、そのまま使えません。カメラ入力なら 80〜150ms、全身動作ならさらに身体慣性 300〜800ms が上乗せされるので、下限は 400ms ではなく **700ms〜1.2秒**になります。移し替える時はここを最初に直してください（`../core/input-layer.md` §3）。

**速度を上げるときは、可視距離を同時に増やさなければならない。** これをやっていないゲームが、後半で理不尽になります。原因は難易度設計ではなく視点です。

### 手段は3つ

**1. キャラクターを画面の後ろ寄りに置く（最も効く）**

進行方向と逆側、**画面の20〜30%の位置**にオフセットする。残りの70〜80%が「これから来るものを読む領域」になります。中央に置くと、可視距離が半分になり、同じ速度で猶予が半減します。

**2. 速度連動FOV（3D）／ズームアウト（2D）**

基準 FOV 60〜75°に対し、最高速で **+10〜15°** まで広げる。同時に、より遠くまでが画面に収まります。

- **補間する。** 1フレームで切り替えると酔いの直接の原因になります。時定数 0.3〜0.5秒程度で追従させる
- **上げ幅を欲張らない。** +20°を超えると周辺の歪みで距離感が狂い、**猶予を稼ぐために入れた変更が、判断を難しくする**という逆転が起きます
- **設定でオフにできるようにする。** 一定FOVでも遊べる状態を保つ

FOV変化は疾走感の演出として語られがちですが、**主目的は先読み時間の確保**です。演出効果は副産物。この順序を取り違えると、演出のつもりで上げ幅を盛りすぎて、遊べなくなります。

**3. カメラを速度に応じて後ろへ引く（3D）**

FOVより歪みが出ないので安全。ただし引きすぎるとキャラクターが小さくなり、接地判定の読み取りが難しくなります。FOVと併用して、それぞれ控えめにするのが扱いやすい。

### 検証方法

「速い」ではなく**猶予の秒数で検証する**。最高速度で、障害物が画面に現れてから対応が必要になるまでの実時間をログに出してください。全速度域で 400ms を下回らないことがリリース条件です（`procedural-generation.md` §4 の走査と同時に回せます）。

## 5. 予兆を地形に埋める

3層フィードバックの Pre（事前）層を、ランナーで実装するとこうなる。**大きな判断を要求する数秒前に、地形そのものに合図を置く。**

| 合図 | 伝えていること |
| :--- | :--- |
| 手前の緩やかな下り坂 | 「速度が乗る」＝この先に距離の要る跳躍がある |
| 崖の手前に立つ看板・旗・杭 | 「ここが端」 |
| 鳥が一斉に飛び立つ、遠くで何かが崩れる | 「何かが起きる」（何が起きるかは言わない） |
| 背景の建物が途切れる | 空間が開ける＝大跳躍 |
| BGMのフィルが入る | 拍の頭に山場が来る |

**置く位置は、必要可視距離（§4）の1.5〜2倍手前。** 予兆を見てから本体が見えるまでに、身構える時間が要ります。予兆と本体が同時に見えると、予兆として機能しません。

**予兆は「何をすべきか」を言わない。** 「何かが来る」だけを伝えるほうが、緊張が強く、かつ学習の余地が残ります。矢印やテキストで「ここでジャンプ」と出した瞬間、それは予兆ではなく指示になり、プレイヤーは世界を読むのをやめます。

**検証**: 初見の被験者が、予兆のある大跳躍と、予兆を外した同じ大跳躍とで、初回成功率に差が出るか。差が出ないなら、その予兆は見えていません。

## 6. 縦の分岐（高所ルート）

同じ区間に2本の高さのルートを通す。**入力を増やさずに選択を作る**、このジャンルで最も費用対効果の高い拡張。

| ルート | 内容 |
| :--- | :--- |
| **高所** | 足場が狭い・間隔が広い。コイン／ブーストが多い。落ちると下のルートへ（即死ではない） |
| **地上** | 安全だが障害物が多く、報酬は少ない |

### 成立条件

- **地上ルートから、高所の報酬が見えていること。** 見えなければ選択は存在せず、ただ難しい道が別にあるだけになります
- **高所からの落下を即死にしない。** 落ちたら地上ルートに合流する。「挑戦して失敗しても、ゲームは続く」がこの構造の価値。即死にすると誰も挑戦しなくなり、分岐が無いのと同じになります
- **入口は跳ぶだけで入れる。** 入口に別の操作を要求した時点で §2 の条件を破っています

生成側の実装は `procedural-generation.md` §7。

## 7. 3Dで速度を見せる

速度は、キャラクターの移動量だけではほとんど伝わりません。**周囲がどう流れるか**で伝わります。

| 手段 | やること | モバイルでの代償 |
| :--- | :--- | :--- |
| **多層パララックス** | 背景を距離ごとに層へ分け、スクロール速度を距離に反比例させる | 層の数だけ描画。4層で十分、モバイルは2層＋空 |
| **カメラのロール（傾き）** | 左右へ動いた時、カメラを進行方向へ **2〜5°** 傾ける。旋回のGが体感として出る | ほぼ無料。**6°を超えると酔う** |
| **放射状スピードライン** | 画面の四隅へ向かって流れる線。速度に応じて濃度を上げる | 画面全体を覆うので、判定領域に被せない |
| **空気遠近法** | 遠いものほど空の色に寄せ、コントラストを落とす | ほぼ無料（フォグ） |
| **トレイル** | 速度に比例して長さ・密度を変える。低速では出さない | パーティクル数に上限を |
| **流れる環境粒子** | 奥から手前へ流れる粒。密度を速度に比例 | フィルレートを食う。半透明の重ねすぎに注意 |
| **風切り音** | 速度でホワイトノイズの音量と低域を上げる | ほぼ無料。最も安く効く |

**フォグの色と空の色を必ず一致させる。** ずれていると遠景が板に見え、奥行きが消えます。3Dランナーで「安っぽい」と言われる原因の上位。

**トレイルと粒子を常時出さない。** 常に出ていると基準がなくなり、速度差が伝わりません。速度が上がった**その瞬間の変化**が情報です。

モバイルでの予算と縮退の判断は `../web-stack.md`。**速度演出は真っ先に発熱する部類**なので、粒子密度は縮退のダイヤルとして最初に用意しておいてください。

## 8. 滞空の静寂と、着地の解放

音でこのジャンル特有に効くのは、鳴らすことではなく**止めること**。

**大ジャンプの滞空中だけ**、走行音（足音・地面のノイズ）をミュートし、BGMにローパスをかける。着地の瞬間に一気に戻す。浮遊感が出て、着地音が解放として知覚されます。

| 条件 | 値 |
| :--- | :--- |
| 適用する滞空時間 | **300ms 以上のジャンプのみ** |
| ローパスのカットオフ | **400〜800Hz** |
| フェード | **60〜100ms**（瞬時に切ると不自然。長すぎると効果が出る前に着地する） |

**小ジャンプに適用しないこと。** 短い跳躍のたびに音がこもると、連続跳躍で音がバタつき（チャタリング）、「音が壊れている」と感じられます。**滞空時間で足切りする**のが要点です。

実装は `../audio/dynamic-music.md`（フィルターの置き場所と、Tone.js 固有の落とし穴）。ジャンプ音そのものの発音遅延については `../audio/platform-and-frameworks.md` §4。**波形の頭に無音があるとその分だけ遅れる**ので、素材の先頭は切り詰めておいてください。デコード済みバッファを持っておくこと（毎回 fetch/decode すると数百ms遅れます）。

コンボでピッチを上げる仕組みは `juice-and-feel.md` §6.1。

## 9. ゴースト・マーカー

前回死んだ地点、または自己ベストの到達地点に、世界の中へ目印を立てる（影、ライン、旗）。**失敗を次回の目標へ変換する**、リトライループの部品。

- **常時表示にしない。** ずっと目印が見えていると「毎回そこで死ぬ」というプレッシャーになります。手前 2〜3秒で見え始める程度に
- **越えたら祝う。** 越えた瞬間に音とエフェクトを返し、マーカーを消す。ここが最も気持ちいい瞬間になります
- **自己ベストと前回の2本まで。** 3本以上立てると景色がノイズになります

リトライループ全体は `juice-and-feel.md` §8。

## 10. この構成が壊れる時

| 症状 | 本当の原因 | 対処 |
| :--- | :--- | :--- |
| 後半が理不尽 | 速度を上げたのに可視距離を上げていない | §4。視点のオフセットとFOV |
| 入力方式を変えたら急に難しい | 猶予・判定窓・休息の数値をタップのまま使っている | `../core/input-layer.md` §3 の5つを直す |
| 「たまに変な動きをする」 | 見えない状態で入力の意味が変わっている | §2。分岐の根拠を画面に出すか、分岐をやめる |
| 上手い人ほど早く辞める | 死亡時に速度を戻しすぎ／速度が線形で頭打ち | §3、`procedural-generation.md` §3 |
| ブーストが嬉しくない | 加速直後に難所が来て、報酬が罰になっている | §3。加速直後は易しい地形 |
| 高所ルートに誰も行かない | 地上から報酬が見えない／落下が即死 | §6 |
| 速く見えない | 周囲が流れていない（キャラだけ動いている） | §7。パララックスと風切り音から |
