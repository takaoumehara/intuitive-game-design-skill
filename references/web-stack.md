# Web技術の選択（モバイル / PC）

「何で作るか」を決める時に読む。ビジュアルと音響の両方を、**スマートフォンで実用に耐えるもの**と**PCの計算資源を前提にするもの**に分けてある。

この分類が最も結果を左右します。Web体験の失敗のかなりの部分は、設計でもデザインでもなく、**PCで作ってPCで確認したものをスマホで出した**ことに起因します。

## 1. 選ぶ前に決める3つのこと

技術名を並べる前に、この3つを確定させてください。ここが決まると選択肢はたいてい1〜2個に絞れます。

| # | 問い | なぜ先に要るか |
| :-- | :--- | :--- |
| **1** | **誰の、どの端末で動くのか** | 「スマホ対応」では足りません。最新のiPhoneか、3〜4年前のAndroidミドルレンジか。後者を想定するなら選べる技術が半分になります |
| **2** | **何分間、連続で動くのか** | 30秒のデモと10分の展示はまったく別の要求です（§2の発熱） |
| **3** | **動かなかった時にどうするか** | 「動かない」で終わる設計と、簡易版に落ちる設計では、選ぶべき技術が変わります（§8） |

**特に2が抜けがちです。** 「デモでは動いた」ものが本番で落ちる原因の大半はこれです。

## 2. モバイルの本当の制約

スマホで動かない理由は「GPUが遅いから」ではありません。実際に効いているのは以下です。

### 2.1 サーマルスロットリング（発熱による性能制限）
スマホは冷却機構を持たないため、**高負荷が続くと端末側が意図的に性能を落とします。** これが「最初は動いていたのに、数分後にカクつく」の正体です。

- **最初の30〜60秒のフレームレートは信用できません。** 計測するなら**3分以上**連続で回してください
- 発熱するとバッテリー消費も跳ね上がり、体験の途中で「熱い」「電池が減る」という別の不満に変わります
- 展示・イベントのように**連続稼働**する用途では、この制約が設計を規定します

### 2.2 実機の差が大きい
同じ「スマホ」でも、ハイエンドとミドルレンジで実効性能は数倍違います。**自分の端末で動いたことは、何の保証にもなりません。**

最低限、以下2つでの確認を勧めてください。
- 想定ターゲットの中で**最も安い/古い端末**
- iOS と Android の両方（描画・音響ともに挙動が違います）

### 2.3 メモリ上限とタブの強制終了
モバイルブラウザは、メモリを使いすぎたタブを**警告なしに落とします**。エラーも出ず、ページが真っ白になるかリロードされます。数十MB以上のアセットを読む設計はここで死にます。

### 2.4 バッテリー・省電力モード
省電力モードではフレームレートが制限され、バックグラウンドの処理も絞られます。ユーザーの多くは省電力モードで生活しています。

## 3. ビジュアル — モバイルで動くもの

描画負荷が小さく、発熱とバッテリー消費を抑えられるもの。

| 技術 | 概要 | モバイル適性の根拠 | 注意 |
| :--- | :--- | :--- | :--- |
| **SVG + CSS / JS** | DOMベースのベクター描画 | 解像度非依存で劣化せず、負荷が極めて低い。UI・ロゴ・図形に最も安全 | 要素数が数千を超えるとDOM操作が重くなる。大量描画には向かない |
| **CSS アニメーション / View Transitions API** | Web標準の遷移・変形 | **ブラウザ側でハードウェア最適化される。最も低負荷でリッチな見た目が出せる** | `transform` と `opacity` に限れば合成のみで済み最速。`width`/`top` などのアニメーションはレイアウト再計算を起こし重い |
| **Canvas API (2D)** | 標準の2Dピクセル描画 | 外部ライブラリ不要で初期ロードが最速。数千個規模のパーティクルまでなら滑らか | 描画命令数がそのまま負荷。オフスクリーンCanvasやスプライト化で軽くなる |
| **PixiJS** | WebGL加速の2D描画エンジン | **描画をGPUに逃がすため、大量の2Dオブジェクトでも滑らか。** スマホの2Dゲームで第一候補 | 約400KB前後。単純なUIには過剰 |
| **p5.js（2Dモード）** | クリエイティブコーディング | 少ないコードで数理造形・インタラクティブアートが書ける。タッチ対応も容易 | **ライブラリが約1MBと重く、内部の抽象化ぶんCanvas直書きより遅い。** プロトタイプ向き。本番で軽さが要るなら Canvas 直書きか PixiJS へ移す |
| **Paper.js** | ベクターグラフィックス | ベジェ曲線・ブーリアン演算などベクター操作が強力 | **Canvas 2D ベースであり、WebGL加速ではありません。** 図形数が増えると重くなります。大量描画なら PixiJS |
| **Rive** | 状態遷移を持つベクターアニメーション | **WASMランタイムが軽量**（数百KB）。アプリ並みの滑らかな状態遷移を低負荷で実現 | デザインツール（Rive Editor）が前提 |
| **Lottie** | After Effects書き出しアニメーション | ベクターなので解像度非依存。単純なアニメーションなら軽い | **「常に軽量」は誤りです。** レイヤー数・マスク・エフェクトが多いJSONはモバイルで明確に重くなります。書き出し時に要素を削るのが前提。`dotLottie` は転送量を削減 |
| **D3.js / React Flow** | データ可視化・ダイアグラム | ノード数が数百程度までなら拡大縮小・操作とも問題なし | D3はSVG描画が基本なので、数千ノードではCanvasレンダラーに切り替えが必要 |

## 4. ビジュアル — PCが要るもの

大規模な3D計算、ピクセル単位の重い処理、大容量のロードを伴うもの。

| 技術 | 概要 | PCが要る理由 | モバイルで使えるライン |
| :--- | :--- | :--- | :--- |
| **Three.js / Babylon.js** | WebGLベースの3D | 単純なモデルならスマホでも動くが、**複雑なメッシュ・動的ライティング・リアルタイム影・多数のテクスチャを重ねると急激に発熱しフレームが落ちる** | ローポリ＋ベイクした影＋テクスチャ圧縮に絞れば実用可。§9の予算参照 |
| **GLSL / カスタムシェーダー（レイマーチング等）** | GPU上のピクセル並列計算 | ShaderToy的な、数式だけで形状を描く手法はピクセルごとの計算量が大きく、**モバイルGPUでは即座にサーマルスロットリングがかかる** | 解像度を落とす（0.5倍でレンダリングして拡大）、ステップ数を減らす、画面の一部だけに適用するなら可 |
| **WebGPU** | WebGLの後継。Compute Shader対応 | 数百万規模のパーティクルやリアルタイム物理を想定した技術で、デスクトップ級GPUが前提 | **モバイルの対応状況は変動が大きい。実装前に必ず現在の対応状況を確認すること**（§10）。WebGL2へのフォールバックを必ず用意する |
| **Unity / Unreal の Web書き出し（WASM）** | ゲームエンジンからのWeb移植 | **初期ダウンロードが数十〜数百MB、メモリ消費も巨大。モバイルブラウザのタブが強制終了しやすい**（§2.3） | 実質的に非推奨。モバイルが要件ならネイティブアプリか、Web用に作り直す判断のほうが速い |
| **ブラウザ内AI推論（Transformers.js 等）** | ブラウザ内で画像生成・推論 | モデルのダウンロード量とVRAM消費が大きく、ハイスペックPCが前提 | 小さいモデル（数MB〜数十MB）の分類・検出タスクなら可。生成系は厳しい |

## 5. 音響 — モバイルで動くもの

実装の詳細は `references/audio/` にあります。ここでは**選択の判断**だけを扱います。

| 技術 | 概要 | モバイル適性の根拠 | 注意 |
| :--- | :--- | :--- | :--- |
| **Web Audio API** | 標準のノードベース音響 | **処理がブラウザ内部（ネイティブ層）で走るため超軽量・低遅延。** 効果音と簡単なBGMはスマホで完璧に動く | 自動再生規制のアンロックが必須。発音数の上限も必要 → `references/audio/web-audio-patterns.md` |
| **Tone.js** | 音楽理論・シーケンサー付きラッパー | **発音数を10〜20に抑えれば**、リアルタイム演奏や自動作曲がスムーズに動く | 約200KB。効果音だけなら過剰 → `references/audio/dynamic-music.md` |
| **Strudel**（TidalCycles の JS 実装） | パターン記述によるライブコーディング | 音源が軽量なサンプラー／簡易シンセなので、スマホのブラウザでもフレーズを鳴らし続けられる | 複雑なエフェクトチェーンを重ねると負荷が上がる |
| **Web MIDI API** | 外部MIDI機器との接続 | 接続自体は軽量。ポータブルMIDIキーボードからWeb上の音源を鳴らす用途に適する | **iOS Safari は Web MIDI に非対応。** Androidは対応。要件に入れる前に必ず確認 |
| **Web Bluetooth API** | センサー・デバイス連携 | 通信自体は軽量 | **対応ブラウザが限られ、iOS Safari は非対応。** HTTPS必須。ユーザー操作起点の接続が必要 |

## 6. 音響 — PCが要るもの

| 技術 | 概要 | PCが要る理由 | モバイルで使えるライン |
| :--- | :--- | :--- | :--- |
| **AudioWorklet + カスタムDSP（C++/Rust/WASM）** | 専用スレッドでのサンプル単位処理 | 極限の低遅延と独自シンセを構築できるが、**演算が過密になるとモバイルの省電力制御で音飛び（クリックノイズ）が出る** | 処理を軽く保てば可。**AudioWorkletは1〜2個まで**。ノード合成で済むならそちらが速く軽い |
| **RNBO（Max/MSP書き出し） / Faust / WebPD** | プロ用音響ツールのパッチをWASM化 | 複雑なモジュラーシンセやエフェクト処理は計算負荷が高く、安定した動作にPC環境が要る | パッチを小さく保てば可。**WASMバイナリの転送量**も評価に入れること |
| **ブラウザ内AI音楽生成（Magenta.js 等）** | ローカルでのメロディ補完・生成 | 推論演算が重く、モバイルでは発熱と生成遅延（テンポのズレ）が出る | 事前生成してキャッシュするなら可。リアルタイム生成は不可 → `references/audio/ai-and-procedural.md` |
| **生成AI の API連携（Suno 等）** | クラウド生成＋Web再生 | **再生自体はスマホでも軽い。** PCが要るのは波形編集・トラック編集などの複雑なUI側 | 再生・ストリーミングのみならモバイルで問題なし。§10のライセンス確認は必須 |

## 7. 音と映像を同時に動かす時

**最も見落とされ、最も厄介な領域です。** 単体では動く2つが、同時に動かすと両方壊れます。

Gibber や Algorave 系の環境（音響合成とWebGLを1つのコードで同時にリアルタイム生成する）が典型ですが、問題自体は**自作でも普通に起きます**。

### なぜ壊れるのか
音声処理には**厳格な締め切り**があります。オーディオスレッドが数ミリ秒でも間に合わないと、その瞬間に「ブツッ」というクリックノイズが出ます。GPUやメインスレッドが飽和すると、この締め切りに間に合わなくなります。

**症状は非対称です。** 描画が重い時は「カクつく」で済みますが、音は「壊れた」と知覚されます。**同じ負荷でも音のほうが体験を大きく損ないます。**

### 対処
- **音を先に確保する。** フレームレートを落としてでも音を守る設計にします。プレイヤーは映像のカクつきより音のノイズに敏感です
- **メインスレッドで重い処理をしない。** 音のスケジューリングはメインスレッドのタイマーに依存するため、描画で詰まるとリズムがヨレます（`references/audio/platform-and-frameworks.md` の先読みスケジューラ）
- **同時に上げない。** 演出の山場でパーティクルを増やし、同時に音のレイヤーも増やすと、そこだけ両方が壊れます。ピークをずらす
- **モバイルでは、どちらかを諦める前提で設計する**（§8）

## 8. 段階的縮退（Graceful Degradation）

**「動く / 動かない」の二択になる技術より、落とせる技術のほうが実務では強い。** これが技術選択の隠れた基準です。

### 縮退しやすい設計

| 落とすもの | 方法 | 見た目への影響 |
| :--- | :--- | :--- |
| **解像度** | `devicePixelRatio` を 1 に固定、または 0.5倍でレンダリングして拡大 | 小さい。最初に試すべき手段 |
| **パーティクル数** | 上限を端末性能で切り替え | 中程度。密度が下がるだけ |
| **エフェクト** | ブラー・反射・影を段階的にオフ | 中程度 |
| **フレームレート** | 60fps → 30fps に固定 | 大きい。ただし**不安定な60fpsより安定した30fpsのほうが快適** |
| **音のレイヤー** | ステム数を減らす | 小さい。音楽的には成立し続ける |

### 実装の型

```javascript
// 起動直後に測るのではなく、しばらく回してから判定する。
// 最初の数秒は端末がまだ発熱しておらず、実力より良い数字が出るため（§2.1）。
let frames = 0, t0 = performance.now();
function measure() {
  frames++;
  const elapsed = performance.now() - t0;
  if (elapsed > 5000) {            // 5秒間の平均で判定
    const fps = frames / (elapsed / 1000);
    if (fps < 40) reduceQuality(); // 段階を1つ落とす
    frames = 0; t0 = performance.now();
  }
  requestAnimationFrame(measure);
}
```

**判定を1回で終わらせないこと。** 発熱は時間とともに進むため、**継続的に測って落とし続ける**必要があります。逆に上げ直すのは慎重に（上下に振動すると、その変化自体が気になります）。

## 9. 予算の数値

**性質**: 実務の経験則であり、端末とコンテンツで大きく動きます。出発点として使い、実機で調整してください。

| 項目 | モバイル（ミドルレンジ想定） | PC |
| :--- | :--- | :--- |
| 初期ロード（総転送量） | **2MB 以下**が安全。5MBで離脱が目立つ | 数十MBまで許容 |
| DOM要素数 | **1,500 以下** | 数千 |
| Canvas 2D の描画オブジェクト | **1,000〜3,000** | 数万 |
| PixiJS のスプライト | **5,000〜10,000** | 数十万 |
| 3D の三角形数 | **100k 以下** | 数M |
| テクスチャ | **2048×2048 まで**、圧縮形式（Basis/KTX2）推奨 | 4096以上も可 |
| 同時発音数 | **16〜32** | 64以上 |
| AudioWorklet | **1〜2個** | 数個 |
| リバーブ（Convolver） | **1個を共有** | 複数可 |
| 目標フレームレート | **安定30fps** を下限、60fps を目標 | 60fps |
| 連続稼働の検証時間 | **3分以上**（発熱を出すため） | 短時間で可 |

## 10. 出典と鮮度

**この章の内容は、他の章より速く古くなります。** 理由は3つあります。

1. **ブラウザの対応状況が変わる。** 特に **WebGPU**、**Web MIDI**、**Web Bluetooth** はブラウザ・OSごとに差が大きく、変動します。要件に入れる前に必ず現在の対応表（MDN、caniuse など）を確認してください
2. **ライブラリのサイズと性能特性が変わる。** ここに書いたKB数・MB数は目安です
3. **生成AIサービスの料金・商用利用条件は頻繁に変わる。** Suno などを使うなら、実装前に現物の規約を確認してください（`references/audio/ai-and-procedural.md` §6）

ユーザーに伝える時は、**断定せずに「確認が必要です」と項目で示す**ほうが有用です。「iOS Safari は Web MIDI に対応していません」のような記述は、この文書を書いた時点の事実であって、永続的な保証ではありません。

§9の数値は実務の経験則であり、査読研究由来ではありません。混ぜて「研究によると」と書かないでください。
