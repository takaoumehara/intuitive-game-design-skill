# 直感プレイテスト & ORIDインタビュー（CARD & ORID Protocol）

**経路D（プレイテストの設計・分析）で使う手順書。** 説明書もチュートリアルも完全に排除してプレイさせ、「知覚されたアフォーダンス」の乖離をあぶり出す。

**このテストで測るもの**: 面白いかどうかではない。**説明なしでどこまで理解できるか**である。楽しさの評価をしたいなら別のテストを設計すること。混ぜると、どちらの結論も出ない。

---

## 1. CARD モデル進行フロー

```text
  [1. CONTEXT]      被験者属性を記録。説明書を物理排除し「30分で自力でルールを解明せよ」と伝える
       │
       v
  [2. ACTIVITY]     試行錯誤を観察。観察者は沈黙を守り、誤操作とタイムスタンプを記録
       │
       v
  [3. REFLECTION]   プレイ直後にORIDインタビューを実施
       │
       v
  [4. DOCUMENTATION] アフォーダンス乖離マップを作成し、次イテレーションの修正案を出す
```

### 1.1 CONTEXT — 被験者属性の記録が結果を読む鍵
以下を必ず記録する。**属性を記録しないテストは解釈不能**になる。同じ物体が集団によって正反対に解釈された観測例が複数あるため（`references/core/case-studies-and-metrics.md` 1.1、1.3）、「n人中m人が分からなかった」という数字だけでは、修正すべきかどうかを判断できない。

- 年齢層
- 該当ジャンルのプレイ経験（時間で聞く。「たまに遊ぶ」は情報量がない）
- 隣接ジャンルの経験（誤ったスキーマの供給源になる）
- 使用デバイスの慣れ
- 対象タイトルの想定ターゲットに該当するか

**目標人数**: 5人。既知の経験則として、ユーザビリティ上の問題の大半は5人で表面化する。10人集めるより、**属性の違う5人**を集めるほうが情報量が多い。

### 1.2 ACTIVITY — 沈黙は手順である
被験者が詰まっている時に助けると、**その瞬間にデータが消える**。詰まりこそが観測対象であり、助けた時点でそのセッションの残りは「教わった人のプレイ」になって比較不能になる。

記録するもの:

| 記録項目 | なぜ記録するか |
| :--- | :--- |
| 最初に注視した / 触れたオブジェクト（＋秒数） | 問い1「初見30秒テスト」の実測値 |
| 意図を持った最初の操作までの時間 | 同上。30秒を超えたら初手の設計が失敗 |
| 誤操作とその時の発話（タイムスタンプ付き） | アフォーダンス乖離の直接証拠 |
| 被験者が声に出した仮説（「これはこうかな」） | 誤ったメンタルモデルの中身が分かる唯一の窓 |
| 諦めた回数・詰まった箇所 | 離脱ポイントの特定 |
| 表情・身体の動き（前のめり、椅子にもたれる） | 言葉より正直。Aesthetics 検証の材料 |

**思考発話法（Think Aloud）**: 「考えていることを声に出してください」と依頼する。ただしこれ自体が認知負荷になり、リズムゲームや高速アクションではプレイを壊す。**時間制約の厳しいジャンルでは使わず、プレイ後の想起インタビューに切り替える。**

**中断の基準**: フラストレーションが強すぎる場合は打ち切る。「30分耐えさせる」ことに価値はなく、被験者が最後の5分で何をしていたかのデータも、疲弊した状態のものになって使えない。

## 2. ORID 会話モデル（インタビュー質問スクリプト）

プレイ直後に実施する。O→R→I→D の順を守る。**いきなり「どうすれば良くなると思いますか」と聞かない。** 事実の想起を先にさせないと、被験者は後付けの物語を作る。

### 2.1 Objective（客観的事実の確認）
記憶が新しいうちに、起きたことを事実として引き出す。

- 「ゲームを開始した時、最初に目に飛び込んできたものは何でしたか？」
- 「どのようなボタン操作・動かし方・タイミングを試しましたか？」
- 「『これがルールだろう』と仮定して試した動きは、全部でいくつありましたか？」
- 「一度も試さなかった操作はありますか？　それはなぜですか？」

### 2.2 Reflective（感情・感触の抽出）
- 「説明書が一切ない状態でプレイしろと言われた時、どう感じましたか？」
- 「特定のオブジェクトに触れた時、直感的に『こう動かすべきだ』と感じましたか？」
- 「操作と音・光・振動が重なった瞬間、どのような心地よさ（または違和感）がありましたか？」
- 「思い通りにいかない時、どのような感情でしたか？　**それは自分のせいだと感じましたか、ゲームのせいだと感じましたか？**」

最後の質問が特に重要。「自分のせい」は再挑戦につながり、「ゲームのせい」は離脱につながる。同じ失敗率でも、この帰属先の違いで結果が正反対になる。

### 2.3 Interpretive（解釈とメンタルモデル）
- 「推測したルールのうち、最もゲームを面白くしたものはどれでしたか？」
- 「推測したルールの中で、矛盾したり進行不能になった瞬間はありましたか？」
- 「オブジェクトの形・色・演出は、ルールの推測を助けましたか？　それとも誤ったルールへ誘導しましたか？」
- 「このゲームで勝つために最も重要だと思った能力は何ですか？」
- 「このゲームは、何のゲームに似ていると思いましたか？」← **既存スキーマの供給源を特定する質問**

### 2.4 Decisional（改善と決断）
- 「もしあなたがデザイナーなら、どのUIやオブジェクトのデザインを最初に修正しますか？」
- 「説明なしでも混乱しないために、追加すべきヒントや仕組みは何ですか？」
- 「もう一度遊びたいですか？　遊ぶとしたら何を試したいですか？」

**注意**: 2.4 の回答は**症状の報告であって処方箋ではない**。被験者は「説明を出してほしい」と言うことが多いが、それは設計の解ではない。要望をそのまま実装せず、2.1〜2.3 の事実から真因を特定して対処する。

## 3. 出力ドキュメント：アフォーダンス乖離マップ

テスト結果はこの形式で文書化し、次イテレーションの修正案とする。

| 対象 | デザイナー意図（Real） | プレイヤー知覚（Perceived） | 発生した問題 | 分類 | 改善策 | 優先度 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 青い時計アイコン | 他人へヒントを出せるリソース | 時間制限のタイマー | 焦って誤操作。5人中4人 | シグニファイア誤認 | 電球／吹き出しアイコンへ変更 | P0 |
| 周縁の光エフェクト | コンボ継続の報酬表現 | 何らかの警告 | 判定エリアから視線が逸れる | Micro/Macro 混線 | 彩度を落とし周縁へ後退 | P1 |
| 装飾用の扉 | 通れない背景 | 開けられる扉 | 3人が扉の前で滞留 | **偽アフォーダンス** | 板を打ち付けた見た目に変更 | P0 |

### 分類の使い分け（優先度の根拠になる）

| 分類 | 意味 | 標準的な優先度 |
| :--- | :--- | :--- |
| **偽アフォーダンス** | できそうなのにできない | **P0**。「バグっている」と解釈され信頼が壊れる |
| **反転マッピング** | 既存スキーマと逆 | **P0**。シグニファイアでは救えず、ルール変更が要る |
| **シグニファイア誤認** | 意図と違う意味に読まれた | P0〜P1。見た目の変更で直るのでコストは低い |
| **隠れ機能** | あるのに気づかれない | P1〜P2。シグニファイア追加で解決 |
| **認知過負荷** | 同時に要求される要素が多すぎ | P1。分割で解決 |
| **フィードバック欠落** | Pre / Immediate / Post のどれかが無い | P1。欠けている層で症状が決まる |
| **アポフェニア創作** | 存在しないルールを発明された | P2。意味のない差異・空白が原因 |

### 優先度をつける原則
**「何人が詰まったか」ではなく「詰まった結果どうなったか」で決める。** 1人しか遭遇しなくても離脱に直結するなら P0、5人全員が遭遇しても自力で回復できているなら P2 でよい。

## 4. 次イテレーションへの引き渡し

乖離マップを作ったら、修正案を `workflows/mechanic-design-pipeline.md` Step 3（CLT/UI設計）へ差し戻す。修正の対処順は常にこの順:

1. **Real を変える**（プレイヤーが期待する挙動そのものにする）
2. **シグニファイアを足す**（形・色・音・振動）
3. **説明を足す**（1と2が不可能だった理由を書き添えて）

同じ被験者に再テストしない。**一度理解した人は、二度と初見にはならない。** 各イテレーションに新しい被験者を用意することが、このプロトコルの運用コストの実体であり、テスト計画時にユーザーへ伝えておくべき制約。
